CALL-FREQUENCY MODEL

  NetworkSession.Update          per session per outer tick

SECTION 0 - FINDINGS FROM THE INITIAL SWEEP (folded in)
================================================================================

P.0a  Parallel.ForEach over a mostly-empty 1000-slot array, ~1000 times/second
      NetworkManager.cs:362

          Parallel.ForEach(sessionMap, ..., s => s?.TickOutbound());

      sessionMap is a fixed-size array sized to MaximumAllowedSessions. The
      SHIPPED config value (Config.js:15) is 1000, while the code default
      (ACE.Common/NetworkSettings.cs:28) is 128.

      With 5 players online this still partitions and dispatches 1000 slots,
      roughly 1000 times per second, to perform 5 slots of real work.
      Parallel.ForEach carries real per-invocation partitioning and
      task-scheduling overhead.

      FIX: maintain a compact collection of active sessions and iterate that
      instead of the sparse fixed array; or fall back to a serial loop when the
      active count is below a threshold, since parallelism is not worth the
      scheduling overhead for a handful of sessions.

      This is plausibly the single largest CPU win in the server.
      [Measured: overstated - see G.C.]

P.0b  Per-tick LINQ allocation and a slow null comparison
      NetworkManager.cs:367
          foreach (var session in sessionMap.Where(k => !Equals(null, k)))
      Allocates an enumerator every tick and uses the static object.Equals
      overload where `k != null` would do.

P.0c  Full-array scans under lock on every login
      NetworkManager.cs - GetSessionCount (~198),
      GetAuthenticatedSessionCount (~211),
      GetSessionEndpointTotalByAddressCount (~245)
      Each performs a full 1000-element scan while holding the session lock,
      on the login path. Running counters, or reuse of the compact
      active-session collection from P.0a, removes them.

P.0d  AcknowledgeSequence materialises the whole dictionary on every ACK
      NetworkSession.cs:692
          var removalList = cachedPackets.Keys.Where(x => x < sequence);
      ConcurrentDictionary.Keys does NOT return a lazy view - it acquires all
      internal locks and materialises a new List of EVERY key, on every ACK
      packet received. With up to 120 seconds of cached packets per session
      (cachedPacketRetentionTime) that is a large allocation plus a lock convoy
      in a per-packet path.
      FIX: iterate cachedPackets directly and TryRemove inside the loop,
      avoiding both the snapshot and the full lock acquisition.
      [Measured: this fix is slower than today - see G.C and NT.7.]

P.0e  Serialisation allocations
      Extensions.cs:17 (WriteString16L) - a GetEncoding(1252) lookup AND a
        fresh byte[] for every string written to every game message, across 100
        call sites. Because cp1252 is single-byte, encoded length always equals
        data.Length, so a bounded stackalloc plus a cached static Encoding is
        safe.
      Extensions.cs:28, 33 (WritePackedDword) - `writer.Write(BitConverter.GetBytes(v))`
        allocates purely to hand bytes to BinaryWriter, which already has
        allocation-free Write(ushort) and Write(uint) overloads emitting the
        identical little-endian bytes. The fix is to delete the allocation, not
        to stackalloc.
      Extensions.cs:51 (Pad) - `writer.Write(new byte[pad])` allocates 0-3
        bytes on every WriteString16L and every Align, so it is very hot.
        Prefer a static readonly zero array over stackalloc here: stackalloc is
        only zeroed because Roslyn emits `localsinit` by default, so if anyone
        ever adds [SkipLocalsInit] the padding would silently become
        uninitialised stack memory written into outbound packets - an
        information leak.
      NetworkSession.cs:425 - `needSeq.ForEach(k => msReqData.Write(BitConverter.GetBytes(k), 0, 4))`
        allocates up to 115 four-byte arrays per NAK. reqData itself escapes
        into reqPacket.Data so it cannot be stack-allocated, but the loop
        should write via BinaryPrimitives.WriteUInt32LittleEndian directly into
        it.
      ConnectionListener.cs:107 - the debug-only `new byte[dataSize]` copy is
        redundant; BuildPacketString already accepts (startPosition,
        bytesToOutput) and is called that way at NetworkSession.cs:799.
      SessionConnectionData.cs:63-65 - a purely local `byte[8]` that never
        escapes; a clean stackalloc candidate, but cold (once per session).

      WHERE stackalloc MUST NOT BE USED: PacketHeaderOptional.cs:74 and
      GameAction/Actions/GameActionSetCharacterOptions.cs:193 derive their
      sizes from CLIENT-SUPPLIED packet data. A stackalloc on an
      attacker-controlled length is a remotely triggerable StackOverflowException,
      which in .NET is UNCATCHABLE and kills the process immediately.
      MessageFragment.cs:91 escapes into ServerPacketFragment.Data.
      NetworkSession.cs:781 already correctly uses ArrayPool.

      BUILD CONSTRAINT: ACE.Server targets net10.0, but ACE.Common,
      ACE.DatLoader and ACE.Entity target netstandard2.0 where Span<T> is not
      in the framework. ACE.Common/Cryptography/Hash32.cs compiles only via a
      transitive System.Memory pulled in by System.Text.Json, which is fragile.
      Any Span work in ACE.DatLoader needs an explicit System.Memory reference
      first.

SECTION A - O(N^2) SERIALIZATION ON ZONE ENTRY
================================================================================

P.1  The heaviest serializer is rebuilt PER OBSERVING PLAYER
     WorldObjects/Player_Tracking.cs:63; WorldObject_Networking.cs:58, 225;
     Creature_Networking.cs:35

     Each observing player calls
     `new GameMessageCreateObject(wo, Adminvision, Adminvision)` INDIVIDUALLY,
     so SerializeCreateObject -> SerializeModelData -> CalculateObjDesc() runs
     once per recipient. For creatures and players CalculateObjDesc does
     EquippedObjects.Values.Where(...).ToList(), three OrderBy passes, and a
     ClothingTable DAT lookup per equipped item.

     When a player enters a crowded landblock that is O(N) heavy
     serializations for the entering player plus O(N) on each observer, plus
     roughly 10 more per creature via TrackEquippedObject - i.e. O(N^2)
     DAT-backed serialization on zone entry. This is the classic "crowded town
     lags on entry" shape.

     FIX: build the message once per (object, adminvision) pair and share it.
     Adminvision is false for essentially all players, so a single cached
     GameMessageCreateObject covers the whole broadcast set. Cache
     CalculateObjDesc() on the WorldObject and invalidate on
     equip/unequip/barber.


SECTION B - PER-RECIPIENT COST IN THE SEND PATH
================================================================================

P.2  Broadcast amplification lives at the FRAGMENT layer, not the message layer
     MessageFragment.cs:91-92

     Good news first: WorldObject_Networking.cs:1378/1419 and Landblock.cs:1213
     correctly share ONE GameMessage across all recipients.

     But at flush time, each session's SendBundle calls CreateServerFragment,
     which does `new byte[dataToSend]` plus a `Buffer.BlockCopy` out of
     `Message.Data.GetBuffer()` - a FULL BYTE COPY of the payload per
     recipient. 100 players x 100 recipients x 60Hz UpdatePosition is roughly
     600,000 byte[68] allocations per second.

     FIX: have ServerPacketFragment reference
     (Message.Data.GetBuffer(), offset, len) instead of owning a copy.
     CreateReadyToSendPacket already only BlockCopys out of it. The buffer is
     only read once the message is built, so sharing it across the parallel
     SendBundle calls (NetworkManager.cs:362) is safe.
     [Measured: rate overstated, and NT.3 is the safer fix - see G.C.]

P.3  Payload Hash32 recomputed per recipient
     ServerPacketFragment.cs:26

     Hash32.Calculate(Data, Data.Length) is an O(size) scan over IDENTICAL
     bytes for every recipient of a shared message. Only the HEADER hash
     differs per recipient (the sequence number).

     FIX: compute the payload hash once per fragment slice on the GameMessage
     and reuse it.
     [Measured: 5.4 ns per recipient; drop it - see G.C.]


SECTION C - PER-TICK OVERHEAD
================================================================================

P.4  12 locks and ~16 DateTime.UtcNow per session per 1kHz tick
     NetworkSession.cs:185-256

     WorldManager sleeps 1ms, so DoSessionWork runs ~1000Hz - but bundles only
     flush every 5ms, so at least 80% of these ticks do nothing useful.

     Per call: one prune check, 4 UtcNow in the InvalidQueue branch, one per
     each of the other 11 groups, and 12 lock acquire/release pairs on
     currentBundleLocks. At 200 sessions that is roughly 3.2 million UtcNow
     reads and 2.4 million lock operations per second.

     FIX: snapshot `var now = DateTime.UtcNow` once, and early-return the whole
     group loop when `now < nextSend && now < nextAck && now < nextResync`
     (still calling FlushPackets()).
     [Measured: the early return does not fire for idle sessions - see G.C
     and NT.1.]

P.5  ArrayPool rent is 8x oversized
     NetworkSession.cs:781

     Rent size is `20 + Data.Length + Fragments.Count * 464`, but a finished
     packet is bounded at 484 bytes (MaxPacketSize 464 + 20 header). An
     8-fragment bundle requests 3732 and rents a 4096-byte array from the
     pool's larger bucket.

     FIX: rent a fixed 484.
     [Measured: not a cost - see G.C.]

P.6  Every property-update message allocates a byte[] under a global lock
     Sequence/SequenceManager.cs:152-188; UIntSequence.cs, UShortSequence.cs,
     ByteSequence.cs (CurrentBytes / NextBytes)

     GetSequence takes `lock (sequenceList)`, and every accessor returns a
     freshly allocated 1/2/4-byte array via BitConverter.GetBytes or
     `new byte[]{...}`.

     PositionPack (Structure/PositionPack.cs:44-53) allocates FOUR of these per
     UpdatePosition. GameMessageUpdateMotion, GameMessageVectorUpdate and all
     GameMessagePublicUpdateProperty* allocate 1-2 each.

     FIX: add WriteCurrentSequence(BinaryWriter, ...) overloads that write the
     scalar directly; retain the byte[] API only for legacy callers.
     [Measured: see NM.4 and G.C.]


P.8  cachedPackets retains every sent packet for 120 seconds
     NetworkSession.cs:73, 756

     Each retained ServerPacket holds its Fragments list and their byte[]
     payloads. At ~20 packets/sec/session that is ~2,400 packets - over 1 MB
     per session - surviving into gen2. At 200 players that is 200 MB+ of
     long-lived garbage churning the GC. AcknowledgeSequence trims it only when
     acks arrive.

     FIX: cap the cache by COUNT as well as age. Retail NAK windows are small -
     MaxNumNakSeqIds is 115 - so retaining 2,400 packets serves no purpose.
     [Measured: see G.C and NT.7.]

P.9  EnqueueBroadcast allocates a LINQ pipeline plus a List per broadcast
     Physics/Common/ObjectMaint.cs:717, called from
     WorldObject_Networking.cs:1393, 1436

     `KnownPlayers.Values.Select(...).OfType<Player>().ToList()` allocates a
     list plus two enumerators under a read lock, for EVERY movement, motion
     and effect broadcast. EnqueueBroadcast(params GameMessage[]) adds a params
     array per call.

     FIX: expose a foreach-friendly enumeration or a pooled reusable buffer,
     and add a single-message non-params overload.
     (Also reported from the Entity side - see perf-entity-server.txt.)

P.10 O(n*m) fragment removal and LINQ in SendBundle
     NetworkSession.cs:870, 896, 933

     Per packet iteration: a fresh List<MessageFragment> removeList, then
     `fragments.RemoveAll(x => removeList.Contains(x))` - a closure allocation
     plus an O(n*m) linear scan - and `fragments.FirstOrDefault()` instead of
     `fragments[0]`. Small n normally, but this runs per packet per session per
     flush.

     FIX: iterate backwards over fragments and RemoveAt; drop removeList
     entirely.


SECTION D - INBOUND PATH
================================================================================

P.11 Inbound datagram processing is fully serialized per port
     ConnectionListener.cs:76-123; ClientPacket.cs:35-36

     One shared buffer per listener means BeginReceiveFrom is only re-armed
     AFTER NetworkManager.ProcessPacket - including CRC search and fragment
     reassembly - returns. Inbound throughput is therefore single-threaded per
     port.

     Per datagram it allocates two IPEndPoints (lines 78, 98), a ClientPacket,
     a MemoryStream, a BinaryReader, and one ClientPacketFragment plus byte[]
     per fragment.

     FIX: multiple in-flight receive buffers (a SocketAsyncEventArgs pool) so
     unpacking overlaps receiving; pool ClientPacket and fragment objects.
     [Measured: overstated as a throughput problem, and concurrent receives
     would race CryptoSystem - see G.C and NT.2.]

P.12 CryptoSystem.Search can walk 256 ISAAC iterations per inbound packet
     ACE.Common/Cryptography/CryptoSystem.cs:30-49

     On the in-order path CurrentKey == x hits immediately, but any reordering
     makes the loop generate and HashSet.Add up to `256 - xors.Count` keys.
     Under packet loss this becomes the dominant per-datagram cost - and it
     runs on the single serialized receive thread (P.11), so it stalls ALL
     inbound traffic on that port.

     Worth instrumenting before optimising. See also bugs-common.txt C.3, which
     describes how this same loop can saturate permanently.

SECTION F - SUGGESTED PRIORITY
================================================================================
  Superseded by the measured priority in G.E; kept for the original reasoning.
  1. P.2  Offset-based fragments. Removes the largest per-recipient
          allocation.
  2. P.1  Share GameMessageCreateObject across observers and cache
          CalculateObjDesc. This is the O(N^2)-on-zone-entry fix.
  3. P.4  Early-return in NetworkSession.Update. Trivial change, removes
          millions of UtcNow reads and lock operations per second.
  4. P.5  Right-size the ArrayPool rent.
  5. P.3, P.6, P.8, P.10 - remaining per-recipient and per-packet allocation.
  6. P.11 Overlapped receive. Larger change; do it after measuring whether the
          serialized receive path is actually a bottleneck at your player
          count.
  8. P.12 Instrument first; optimise only if the loss path proves hot.

CROSS-CUTTING NOTE: P.1, P.2 and P.3 are all the same underlying problem -
work that should happen once per message is happening once per recipient. In a
crowded landblock that is the difference between O(N) and O(N^2). Fixing them
together is substantially more valuable than any one alone.

CONTEXT ESTABLISHED WHILE MEASURING (several findings depend on it)
  - DoSessionWork's Parallel.ForEach uses NetworkManagerParallelOptions, whose
    MaxDegreeOfParallelism = max(vCPU * WorldThreadCountMultiplier, 1)
    (ACE.Common/ThreadConfiguration.cs:32-44). With the Config.js.example
    multiplier 0.34 on 5 vCPUs or fewer that is 1, so every session is ticked
    inline ON THE WORLD THREAD. Either way the world loop waits for
    DoSessionWork, so its cost is on the world thread's critical path.
  - NetworkSession.Update is not single-threaded per session, despite the
    comment at NetworkSession.cs:246. AuthenticationHandler.cs:41 (account name
    over 50 characters) -> NetworkManager.SendLoginRequestReject ->
    session.Network.Update() (NetworkManager.cs:195) runs on the RECEIVE thread
    for a session already in sessionMap. Rare, but every buffer-reuse design
    below has to survive it.
  - CryptoSystem (ACE.Common/Cryptography/CryptoSystem.cs) mutates ISAAC state
    and a plain HashSet<uint> on every inbound packet with no synchronisation,
    so one session's inbound packets must never be processed concurrently.
  - GameMessages die young: only bundle queues reference them until the next
    flush, and cachedPackets holds copies, not messages. Their GC cost is the
    gen0 allocation rate.


--- G.1 TRANSPORT AND SESSION LAYER --------------------------------------------

NT.1 [HIGH] Idle session tick: 182 ns per session per tick; a dirty-group mask
     cuts it to 12 ns
     NetworkSession.cs:185-256 (Update); Session.cs:121-178 (TickOutbound)

     Every ~1 ms, every session takes 12 lock/unlock pairs and reads
     DateTime.UtcNow 4 times, even with nothing queued.
     Measured per idle session (on this VM DateTime.UtcNow costs 17 ns and an
     uncontended lock 8.5 ns); re-run independently with the same result:
         current                                           182 ns
         P.4 exactly as written (see G.C)                  111 ns
         clock read once + dirty mask (prototype)           12 ns
     At 1000 sessions that is ~180 us per DoSessionWork call - roughly 15% of
     the world thread at ~1000 calls/s when DOP=1 - against ~12 us.

     FIX:
       (a) Read the clock once per DoSessionWork and pass it down; keep the
           public Update()/TickOutbound() as wrappers.
       (b) Add an int dirtyMask to NetworkSession. EnqueueSend and FlagEcho set
           the group's bit INSIDE the group lock (Interlocked.Or). Update reads
           the mask with Volatile.Read and locks only groups whose bit is set.
           A bit is cleared (Interlocked.And) only under that group's lock,
           when its bundle is swapped. Ack and time-sync timers are compared
           lock-free, taking group 0's lock only when due.
     SAFETY: no lost wakeup, because bits are set and cleared under the same
     group lock; an enqueue that races the mask read goes out next tick, as
     today. Re-check now >= nextSend inside the lock to keep the
     one-bundle-per-5-ms behaviour. Not verified: Harmony mods patching
     Update/TickOutbound.
     Confidence: VERIFIED (prototype measured; concurrency argument reasoned).
     [Review: real figures and the loop rate are in H.B; see also H.2.]

NT.2 [HIGH] The receive loop allocates 527 B per datagram; a dedicated blocking
     receive thread allocates 0 B and used the least CPU
     ConnectionListener.cs:74-145 (new IPEndPoint at 78 and 98, EndReceiveFrom,
     Task.Run at 142)

     Loopback, 64 client sockets, 200k datagrams, two repetitions. Process CPU
     per datagram includes a ~2.5 us sender:
         R1 current APM BeginReceiveFrom                      527 B   7.4-11.3 us
         R2 await ReceiveFromAsync(Memory, SocketAddress)       0 B    7.5-9.2 us
         R3 dedicated thread, blocking
            ReceiveFrom(Span, SocketFlags, SocketAddress)       0 B    4.4-4.8 us
         R4 = R2 plus materialising an IPEndPoint              72 B
     SocketAddress.Equals costs 2.0 ns and 0 B (IPEndPoint.Equals 0.6 ns).

     FIX: one background thread per listener running
         while (!stop) { n = socket.ReceiveFrom(buffer, SocketFlags.None, addr);
                         try { process } catch (Exception) { log and drop } }
     Cache each client's SocketAddress on Session (EndPointC2S.Serialize()
     once), validate with SocketAddress.Equals, and build an IPEndPoint only on
     the LoginRequest / ConnectResponse paths. This also removes the recursion
     and the Task.Run hop, and gives the N.0a containment point
     (bugs-network.txt). Shutdown: Close() makes the blocking call throw
     ObjectDisposedException or SocketException; exit the loop on those.
     COMPATIBILITY: NetworkManager.ProcessPacket(ConnectionListener,
     ClientPacket, IPEndPoint) is public; add a SocketAddress overload and keep
     the old one.
     Confidence: allocation VERIFIED; the CPU ordering VERIFIED on Linux only.
     [Review: validation verified; on Linux this also removes ~7 us of CPU per
     packet SENT - see H.1. Use the blocking form, not ReceiveFromAsync.]

NT.3 [HIGH for allocation and retention, MEDIUM for CPU] Serialise each
     outbound packet once into an exact-size wire byte[], and cache that
     instead of the ServerPacket object graph
     NetworkSession.cs:734-760 (FlushPackets), 779-826 (SendPacketRaw),
     834-951 (SendBundle); MessageFragment.cs:91-92; ServerPacket.cs:37-72

     Per flush today:
       - a NetworkBundle with its Queue;
       - a List<MessageFragment>, plus a MessageFragment per message;
       - per packet: a ServerPacket, a PacketHeader, a List<PacketFragment>, a
         removeList with a RemoveAll closure, and a params ServerPacket[1]
         (line 949);
       - per fragment: a ServerPacketFragment, a PacketFragmentHeader and a
         byte[] copy of the payload;
       - for optional headers: a MemoryStream, a BinaryWriter and a byte[32];
       - a ConcurrentDictionary node.

     Prototype:
       - Fragment cursors are a List<struct>, mutated by ref through
         CollectionsMarshal.AsSpan.
       - Each packet is assembled in a [ThreadStatic] scratch buffer: headers
         written with BinaryPrimitives, the payload copied straight from
         Message.Data.GetBuffer(), hashes accumulated while writing. It is then
         copied to an exact-size byte[] in a small OutPacket.
       - At flush, the sequence, time, flags and checksum are written into the
         header bytes. The header hash is plain arithmetic, because Hash32 is a
         sum of little-endian words.
       - A retransmit copies the wire bytes to a stackalloc span, sets the
         Retransmission flag and re-checksums. The cached copy is never
         mutated.
     Datagrams AND retransmits were byte-identical to a verbatim copy of the
     current path over 6 scenarios x 50 flushes, including the N.0c 896-byte
     boundary case.

     Measured per flush (current -> prototype):
         1 x 60 B message             858 B / 245 ns  ->   210 B / 199 ns
         6 small messages            2146 B / 490 ns  ->   578 B / 188 ns
         ack + echo only              482 B / 123 ns  ->   146 B /  57 ns
         ack + echo + 3 small        1386 B / 302 ns  ->   370 B / 124 ns
         1500 B + 3 small            3938 B / 809 ns  ->  2346 B / 491 ns
     Retained per cached packet: 358-1174 B in ~10 objects -> 166-598 B in 2.
     At ~30k flushes/s that is roughly 40 MB/s -> 11 MB/s of gen0 allocation.

     Design points:
       - Convert the public EnqueueSend(params ServerPacket[]) packets
         (ConnectRequest, Referral, RejectRetransmit, NAK) to OutPacket at
         enqueue, so there is one queue type.
       - Add a packet to the retransmit cache AFTER its first send.
       - Reuse bundles through a double buffer whose spare is handed over UNDER
         the group lock, which survives the concurrent-Update path above
         (measured 136 B / 23 ns -> 0 B / 13 ns per swap).
       - Do NOT ArrayPool the wire arrays. Their lifetime spans the tick-thread
         send, receive-thread retransmit, ack/prune removal and
         ReleaseResources.
     Subsumes P.2, P.5 and P.10.
     COMPATIBILITY: SendBundle/FlushPackets/SendPacketRaw are private but
     Harmony-patchable by name; ServerPacket and Packet.Fragments stay public.
     Not verified: mods reflecting on cachedPackets.
     Confidence: VERIFIED (byte parity and measurement).
     [Review: bytes confirmed on the real path; times understated 3-7x, and
     the "ack + echo + 3 small" scenario cannot occur - see H.B.]

NT.4 [MEDIUM, trivial] SendTo with an EndPoint allocates 40 B per packet
     NetworkSession.cs:805
     SendTo(byte[], int, SocketFlags, EndPoint) allocates 40 B per call.
     SendTo(ReadOnlySpan<byte>, SocketFlags, SocketAddress) with a cached
     SocketAddress allocates 0 B. Cache the SocketAddress for EndPointC2S /
     EndPointS2C on Session and refresh it in SetS2CEndpoint. ~1.4 MB/s at
     ~35k packets/s. Confidence: VERIFIED.

NT.5 [MEDIUM, trivial] EnqueueSend(params GameMessage[]) allocates a
     GameMessage[1] on every call, and per RECIPIENT in ranged broadcasts
     NetworkSession.cs:118
     There are 1,704 `Network.EnqueueSend(` call sites, nearly all
     single-message. Per-recipient callers include WorldObject_Networking.cs:1408
     (EnqueueBroadcast(msg, range): local chat, spell words, emotes, ranged
     motion) and PlayerManager.cs:644.
     Measured 32 B per call (40 B for two messages). A single-message overload,
     or `params ReadOnlySpan<GameMessage>` (C# 13+), is 0 B. Recompiling ACE is
     enough; no call sites change.
     COMPATIBILITY: keep the array overload so compiled mods still bind. A
     Harmony patch on EnqueueSend(GameMessage[]) - a plausible "intercept all
     outgoing messages" mod - would silently stop seeing most traffic. Route
     every overload through one private method and document it as the patch
     point. Found independently by both passes (also NM.5).
     Confidence: VERIFIED.

NT.6 [MEDIUM] Inbound parse allocates 736-1104 B per datagram
     ClientPacket.cs:23-53 (MemoryStream + BinaryReader at 35-36);
     PacketHeaderOptional.cs:22 (a field-initialiser MemoryStream for EVERY
     packet), 28 (new BinaryWriter), 32/85/93/100 (ReadBytes copies);
     ClientPacketFragment.cs:20

     PacketHeaderOptional re-serialises the bytes it has just read into a
     MemoryStream, whose first write allocates 256 B, purely to Hash32 them.
     For steady-state flags those bytes are exactly
     buffer[20 .. 20+optionalSize].

     Measured including CRC verification and a ClientMessage per fragment,
     parity checked over 2000 packets of each kind:
                               current           V2              V3

P.0d THE PROPOSED FIX IS SLOWER THAN TODAY. Enumerating the ConcurrentDictionary

  - NetworkStatistics Interlocked increments: 3.9 / 4.6 / 5.0 ns with 1 / 2 / 4
    threads. No meaningful false sharing.
  - DateTime.UtcNow per inbound packet (NetworkSession.cs:337): 17 ns.

    misses per packet. Not worth restructuring.

    overhead is MemoryStream 64 B + BinaryWriter 40 B per MESSAGE, not per
    recipient. The rewrite would break the public Data / protected Writer API
    of ~160 subclasses and of mods. The real costs are property and sequence
    reads, not writes.
  - FrozenDictionary for the inbound handler maps: ~10k lookups/s, and mods may
    insert handlers reflectively.
  - A ref-struct inbound reader instead of ClientMessage: ~300 B per message at
    a few thousand messages/s, across 152 handlers plus mods.
  - MovementData.Serialize() / ToArray (MovementData.cs:177): dead code.

    ViewContents, FellowshipFullUpdate, AllegianceUpdate, house payment LINQ:
    per click or per login.
  - An interpolated-string handler for SystemChat: possible, but back-patching
    the length prefix is not justified at its rate.
  - GameEvents cannot be shared across recipients: they carry the recipient's
    guid and a per-session event sequence.
  - Converting PacketHeader / PacketFragmentHeader (public classes) to structs

      - GameMessage must stay a shared, mutable class.
      - `readonly record struct` only adds value equality and ToString. The

         at call 12. Order is by group index, not enqueue order.
       - Ack, echo and time-sync are set only on group 0's bundle, and no
         message type uses group 0. They therefore always travel as their own

         expect delays of one or two windows, not starvation.

       - flush every ready group in the same Update(), as separate packets as
         today. Same packet count, no waiting.
       - let the ack / time-sync / echo headers ride on the next data packet of
         any group (WriteOptionalHeaders already runs for every bundle).

CORRECTIONS
H.1  ReceiveFromAsync is NO BETTER than today's APM receive, rather than
     worse: 10.5-10.7 us against 9.6-10.8 us per send in these runs, which is
     within the noise. The advice stands: it does not fix the send cost, and
     the blocking receive thread does.

H.2  WHO IT AFFECTS. At the shipped WorldThreadCountMultiplier of 0.34, the
     session tick runs at DOP max(vCPU x 0.34, 1):
       - 1 below 6 vCPU;
       - 2 at 6-8 vCPU;
       - 3 at 9-11 vCPU;
       - 4 at 12 vCPU.
     So H.2 applies to hosts with 6 or more vCPU. It also applies to any
     Config.js without the multiplier key, where the DOP is unlimited
     (bugs-common.txt C.2).
     SIZE. "Doubles" is the case with the ack and time-sync timers pushed out.
     With the real timers running the increase is about 30% (259 -> 332
     ms/s), because at DOP 1 the sends already wake the thread pool (H.1).
     H.1 and H.2 act on the same worker wake-ups, so do not add their savings.

NT.3 (H.B) THE RATIO IS 2-5x, NOT 3-7x. H.B subtracts a bare sendto from the
     real total. Counting user CPU only, from the same run
     (net-e2e/results/flush.txt), the real managed flush is real minus
     bare-sendto user time:
         1 x 60 B             542 ns    2.2x Section G's 245 ns
         6 small            1,177 ns    2.4x Section G's 490 ns
         ack + echo only      669 ns    5.4x Section G's 123 ns
         1500 B + 3 small   1,789 ns    2.2x Section G's 809 ns
     Against the copy run under the same conditions it is 1.6-2.2x. H.B's
     conclusion holds: the prototype's time ratios do not carry over.
