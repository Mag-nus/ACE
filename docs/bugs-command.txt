FINDINGS FROM THE INITIAL SWEEP (folded in)
  These are two further instances of the X.5 pattern below - a parameter-count
  guard that does not match the highest parameters[] index actually read.

  X.0a  AdminCommands.cs:1217-1229 - `@adminhouse dump hid`
        The guard `parameters.Length > 1` only guarantees 2 parameters, the
        `if (parameters.Length < 2)` at line 1218 is dead code, and line 1224
        unconditionally reads parameters[2]. Typing `@adminhouse dump hid`
        with 2 params throws IndexOutOfRangeException. It is caught by
        GameActionTalk.cs's outer try/catch and only logged, so the admin sees
        a silent failure with no usage message.

  X.0b  AdminCommands.cs:3747-3823 - `@qst bits on/off/show`
        For `bits on` and `bits off` the guard is `parameters.Length < 3`
        (lines 3749, 3783) but the code reads parameters[3] (3762, 3796) -
        it needs < 4. For `bits show` the guard is `< 2` (3817) but it reads
        parameters[2] (3823) - it needs < 3.
        The sibling bestow/erase/stamp subcommands in the same method
        (3648-3732) get this right, confirming these are copy-paste slips
        rather than intent.

Read Section A first: any player can claim any retail character (X.2), and on
`combined` the restored character keeps retail staff abilities (X.1).

SECTION A - CRITICAL: /restoreretailcharacter
================================================================================

X.1  A restored retail staff character keeps staff abilities  [`combined` only]
     Command/Handlers/CharacterTransferCommands.cs:136-151 (ints), 154-168 (bools)
     [VERIFIED DIRECTLY]

     The command is registered at AccessLevel.Player and copies every property
     of an arbitrary retail biota onto the new character. The bool loop skips
     Attackable and the four permission bools (IsAdmin, IsArch, IsSentinel,
     IsAdvocate), so command authorisation is not reachable. Everything else a
     retail GM, sentinel or advocate carries is copied:

       IsPsr                      advocate teleport by map click
       Invincible                 cannot be damaged
       IgnorePortalRestrictions   uses any portal regardless of level/quest
       IgnoreHouseBarriers        walks through house barriers
       SafeSpellComponents        casting consumes no components
       HiddenAdmin, AdvocateState staff display state
       IsEnvoy                    accepted by CommandManager.cs:298-311 for
                                  Envoy, Sentinel and Advocate commands. ACE's
                                  own id (9005), so not expected in retail data.
       AdvocateQuest, AdvocateLevel
                                  inputs to the Advocate self-elevation at
                                  Player.cs:178-181; harmless without IsAdvocate
       CloakStatus, PhysicsState  PhysicsState carries the Cloaked bit
       ChannelsActive/Allowed     staff chat channels

     Nothing clears these at login: WorldManager strips them only from
     characters with an Admin or Sentinel WeenieType, and the restored character
     is built from the "human" weenie.

     FIX: skip these properties too. `RetailCharacterImport` does this with two
     sets, privilegeBools and privilegeInts, matching the list WorldManager
     strips plus the permission and advocate properties. Cherry-pick 2de3a2f9c.

X.2  Same command: no ownership proof, no enable gate, no rate limit
     CharacterTransferCommands.cs:28-47, 269-343

     Any player can name ANY retail character on nine hard-coded shards and
     receive its full inventory, wielded gear, levels, skills and titles.

         /restoreretailcharacter ff SomeFamousPlayer Mule

     FIX: require an ownership token or admin approval, and gate behind a
     server property, disabled by default.

X.3  Same command briefly mutates the SHARED CACHED weenie
     CharacterTransferCommands.cs:73-84

         var tempCreateList = human.PropertiesCreateList;
         human.PropertiesCreateList = null;
         var player = new Player(human, guid, session.AccountId);
         human.PropertiesCreateList = tempCreateList;

     `human` is the shared entry from DatabaseManager.World.GetCachedWeenie.
     The list is restored, but with no try/finally: if the Player constructor
     throws, every character created server-wide loses its starter create-list
     until the cache is reloaded. While the window is open, a character created
     on another thread also gets none. This runs on the DB callback thread.

     FIX: clone the weenie before mutating, or skip the create-list at the
     character-creation call site.

SECTION C - CRASHES FROM PLAUSIBLE INPUT
================================================================================

X.5  Parameter-count guards that do not match the highest index read
     DeveloperLootCommands.cs:30   `testlootgen` declares parameterCount:1 but
                                   reads parameters[1] with no length check.
                                   Its sibling testlootgencorpse (line 103) HAS
                                   the `parameters.Length < 2` guard -
                                   confirmed copy-paste slip.
                                   Trigger: `testlootgen 100`.
     DeveloperCommands.cs:226-241  `echo` declares no parameterCount and
                                   dereferences parameters[0] INSIDE ITS OWN
                                   CATCH - so `@echo` with no args throws at
                                   parameters[1] and the catch handler throws
                                   again at line 241. Sibling playsound
                                   (line 248) declares parameterCount:1.
     AdminCommands.cs:3894-3896    `@qst fellow list <filter>` reads the filter
                                   from parameters[1], which is literally
                                   "list", and guards Length >= 2 instead of
                                   >= 3. The non-fellow sibling at 3615-3617 is
                                   correct. Result: filters all quests by
                                   "list" and always reports "No quests found".

X.6  Missing return after an error path leads to a null deref on the DB thread
     AdminCommands.cs:4099-4104 (@rename, Envoy)

     After reporting "cannot be found" the method does not return, so
     DatabaseManager.Shard.RenameCharacter(null, ...) throws NRE on the
     database thread.

     REACHABLE because line 4093 GetCharacterStubByName(oldName) matches
     exactly, while PlayerManager.GetOfflinePlayer (PlayerManager.cs:245) also
     matches "+"+name - so `@rename Admin Guy, Bob` for a character stored as
     "+Admin Guy" nulls both. Also line 4059 newName.First() throws on
     `@rename Old Name,`.

     FIX: return on null, null-check the stub, validate newName non-empty.

X.7  Empty-string parameters reach handlers that index the first character
     DeveloperCommands.cs:929

     `paramValue[0]` runs before any emptiness check.
     CommandManager.ParseCommand (CommandManager.cs:213-239) produces
     empty-string parameters from `""`, so `@setvital hp ""` throws
     IndexOutOfRangeException. This quoting trick reaches EVERY handler that
     indexes a parameter's first character.

     FIX: string.IsNullOrEmpty check first (TryParse already follows).

X.8  Unvalidated numeric parsing
     DeveloperCommands.cs:1584  float.Parse(parameters[0]) - `@teledist abc`
                                throws, and `@teledist NaN` PARSES and
                                teleports the player to a NaN position,
                                corrupting physics state.
                                AdminCommands.LastSpawnPos is also null-deref'd
                                on a fresh server.
     DeveloperCommands.cs:395   Convert.ToInt16
     AdminCommands.cs:4358,4399,4426  bool/long/double.Parse (masked by a
                                catch-all)
     AccountCommands.cs:79      `accountget nosuchuser` NREs on a null account

     FIX: TryParse throughout, plus float.IsFinite on any position value.


SECTION D - THREADING
================================================================================

X.9  Shared state mutated from database callback threads, off the world tick
     AdminCommands.cs:3550-3567 (@morph) calls PlayerManager.AddOfflinePlayer,
       session.Characters.Add (a plain List, read by the world thread) and
       session.LogOffPlayer() from the callback.
     AdminCommands.cs:2906 (@god -> DoGodMode) rewrites attributes and vitals

     CharacterTransferCommands.cs:62-404 performs the ENTIRE import - GUID

       `// todo` admitting this.

     FIX: marshal the callback body onto an ActionChain or world-thread
     enqueue.

NOTE ON METHOD: X.5 confirms the pattern already seen across this audit -
where one branch of a method guards correctly and an adjacent branch does not,
it is a copy-paste slip rather than intent. A systematic sweep comparing every
handler's parameterCount and length guards against the highest parameters[]
index it actually reads would likely find several more.
