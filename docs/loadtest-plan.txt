================================================================================
LOAD-TEST RUN PLAN AND RESULTS (vm8)
================================================================================
Scope   : whole-server load tests of ACE.Server on a Linux VM, with the
          /loadtest command (branch LoadTest), and A/B tests of code changes
Date    : 2026-11-27 (pass 1 ran 2026-11-26)
Status  : RUNNING. Sections B and E are updated after each run and analysis.
Companion: perf-physics.txt Section S (the findings), vm8-README.txt and
           vm8-summary.tsv in .ace-traces/Local (the raw data)

The runs measure where ACE spends CPU and memory under a whole-server load,
then A/B-test code changes against that baseline. A change counts only if it
beats the base-to-base noise (about 1%) and behaves the same. Memory is
reduced in code first, driven by heap data. GC settings are tested only after
that.

SECTION C - WHAT EACH TEST IS FOR, AND WHY
================================================================================

C.1  Physics fixes end to end (runs 1-8)
     QUESTION: what do the physics fixes, verified on single objects in
     perf-physics.txt R.4, save on a whole server with GC, threads, AI and
     generators running?
     DESIGN: ABBA order (base, q5, q5p, q5pa, q5pa, q5p, q5, base), so slow
     drift over the day cancels out. Dungeon load, because it is steady.
     MEASURES: process cores, world update time per tick (UpdateGameWorld),
     Monster_Tick, allocation MB/s, GC count, pause per GC, worst tick.
     WORTHWHILE IF: CPU falls clearly more than the ~1% noise in both halves
     of the ABBA, or allocation falls a lot, with no new errors in the logs.
     q5pa is in the set to test whether AFrame as a struct pays more than its
     bytes (C.4).
     RESULT (14:00): worthwhile, every step. q5pa uses 10.4% fewer cores and
     allocates 63% less than base. Both ABBA halves agree within 1.1 points,
     and no new error types. PC.4 pays far more than in the single-object
     harness. DATAS runs fewer GC heaps as allocation falls, so each pause
     gets longer. See D.8, D.10 and perf-physics.txt S.6.

C.2  What the memory is (runs 9-10)
     QUESTION: which objects make up the 6.5-7.5 GB live heap and the 1-5.7 GB
     of gen2 free space, and is any of it growing?
     DESIGN: base, dungeon load, 60 min. A forced full GC at 15, 20, 30, 40,
     50 and 60 min reads the live heap over time; heap dumps at 20 and 60 min
     give counts and bytes by type; allocation trace at 18 min.
     OUTPUT: the types to fix first. Memory-fix variants are then written and
     A/B-tested like C.1.
     RESULT (15:20): the live heap is 5.75-5.93 GB and flat after 40 min.
     About 2.7 GB of it is copies of the same cell geometry: 134,117 physics
     CellStructs built from 958 distinct ones (perf-datloader.txt P.4). Three
     smaller items are new. See D.11 and perf-physics.txt S.7.

C.3  Replicate pass 1 (runs 11-16)
     QUESTION: are pass 1's single-run results real? R.2 showed 3.4% fewer
     cores on the dungeon load; PG.1 showed nothing beyond noise.
     DESIGN: the same six configurations, in reverse order. The surface runs
     also give a second sample of how much the surface load varies.
     CHANGED 15:10: runs 12 and 15 (PG.1 alone) skipped. PG.1 is part of
     q5, which C.1 measured, and their two hours went to the memory test.
     SURFACE RESULT (runs 11 and 13 against pass 1): no difference beyond the
     load's variation. Cores per 1,000 loaded landblocks: base 0.240 and
     0.246; pg1 0.207; pg1r2 0.253 and 0.241.
     DUNGEON RESULT (runs 14 and 16): R.2 replicates. pg1r2 against base,
     cores -3.4% in pass 1 (1.546 / 1.600) and -2.8% in pass 2 (1.582 /
     1.627); Monster_Tick -5.9% and -3.9%; world update -2.7% and -1.9%.
     PG.1 alone was -0.6% in pass 1, so most of it is R.2. Allocation and
     GC are the same in all four runs. Run 26-27 (q5par2) test it on top
     of q5pa.

C.4  Why each young GC stops the world for ~25 ms (analysis only)
     From the GC events already in each run's CPU trace: suspension, mark time
     per root kind per heap, and the rest of the collection.
     WHY: if marking old-to-young references (card marking) is most of it,
     struct conversions (PC.4, M.4) are worth more than their byte counts,
     because they stop old objects pointing at new garbage.
     RESULT (10:06): card marking is 8-13 ms of each gen0 pause and moving the
     survivors most of the rest; see D.4 and perf-physics.txt S.4.

C.5  Colour-phase landblock ticking (runs 31-35)
     QUESTION: can the surface reach its 60 Hz target? Today one landblock
     group holds most surface landblocks, so the "multi-threaded" tick runs on
     about one thread: 39 updates a second on 1.45 of 8 cores
     (perf-physics.txt S.1).
     CHANGE: tick landblocks in 16 phases by (x mod 4, y mod 4). Landblocks of
     one colour are at least 4 apart, the spacing the groups already
     guarantee between groups, so each phase runs in parallel. Each
     landblock's tick still sets its own group as the current group, so the
     game code's same-group checks keep their meaning. Dungeon landblocks run
     in the first phase.
     DESIGN: the same binary with the switch off and on, ABBA, because surface
     runs vary. One dungeon run with it on checks the dungeon load does not
     get slower.
     WORTHWHILE IF: world update well under 16.7 ms and close to 60 updates a
     second on the surface, with no cross-thread errors in the logs.
     Since more updates per second is more work per second, compare time per
     update and updates per second, not cores.

C.6  The physics fixes and the CellStruct cache on the surface (runs 17-22)
     QUESTION: does q5pa's dungeon result hold at 50,000-80,000 creatures?
     Does sharing CellStruct (q5pacs) take enough off the heap that the
     working set stays below the ~12.5 GB where the blocking compactions of
     D.2 start?
     DESIGN: ABCCBA (base, q5pa, q5pacs, q5pacs, q5pa, base), because surface
     runs vary. Each pair is compared within the same night.
     MEASURES: as C.1, plus the live heap and working set, and the number and
     length of blocking gen2s. The collection count follows free memory on
     the surface (D.12), so compare the builds by total pause and worst
     pause, not by collection count.
     WORTHWHILE IF: the blocking compactions and their 1.3-4.3 s pauses stop,
     or the working set falls by GBs, with no new errors.
     RUN 19 (q5pacs): the lowest surface load so far, 5,930 landblocks and
     56,900 creatures on average (runs 17-18: 6,944 and 7,492). One 5 s
     interval with over 1 s of GC pause (3.55 s), against 5 and 8 in runs
     17-18; peak RSS 11.5 GB; lowest MemAvailable 2.0 GB. Total pause 66 s
     against 118 and 100 s. The load is too far from the others to
     credit the cache. Live heap after each gen2 against loaded landblocks,
     fitted within each run, puts every surface run at 6.3-7.3 GB at 7,000
     landblocks; q5pacs is at 6.6 GB, inside that spread. A saving under
     ~1 GB would not show on the surface. The dungeon runs (C.7) measure it
     at a fixed load.
     RUN 20 (q5pacs): 6,095 landblocks and 59,500 creatures, about the load
     of pass 1 base and pg1r2 (6,050 and 6,116, a day earlier). Against
     them: cores 1.423 against 1.450 and 1.550, world update 23.2 against
     25.1 and 25.4 ms, allocation 144 against 243 and 260 MB/s, total pause
     68 against 95 and 88 s. But 3 blocking compactions (3.64, 2.31,
     3.03 s) against 2 and 8, the same 12.0 GB peak working set, and the
     same ~1.5 GB lowest MemAvailable. So the cache does not keep the
     surface out of the compaction zone. q5pacs contains q5pa's physics
     fixes, which cut allocation; runs 21-22 give q5pa and base on the same
     night to separate the two.
     RUN 21 (q5pa): 5,484 landblocks and 58,700 creatures, the lowest load
     so far; the same build loaded 7,492 in run 18. No 5 s interval with
     over 1 s of GC pause and no blocking gen2: memory load peaked at 85%
     (lowest MemAvailable 2.18 GB, peak RSS 11.2 GB). Total pause 56 s.
     Against run 19 (q5pacs, 5,930 landblocks): cores 1.199 against 1.423,
     world update 22.1 against 19.4 ms, allocation 123 against 132 MB/s.
     The two builds show no difference that the load does not explain.
     One build's landblock count varies by 27% between runs, so whether a
     run reaches the compaction zone follows the landblocks it loads
     (D.2), not the build.
     RUN 22 (base): 5,781 landblocks and 57,000 creatures, 5% more than run
     21 the hour before. Against run 21 (q5pa): cores 1.456 against 1.199,
     world update 23.0 against 22.1 ms, monster tick 6.16 against 5.06 ms,
     allocation 247 against 123 MB/s, total pause 70 against 56 s. It
     reached 91% memory load (lowest MemAvailable 1.42 GB, peak RSS
     12.3 GB) and had 2 blocking compactions (3.19 and 3.13 s) against
     none.
     RESULT (runs 17-22): q5pa's halving of allocation holds on the
     surface: 123-160 MB/s in all four q5pa and q5pacs runs, against
     243-268 MB/s in all four base runs. It used fewer cores at a similar
     load (18% fewer in run 21 than run 22, at 5% fewer landblocks), but
     the surface load is too uneven to put a firm number on that (D.14).
     Neither build keeps the surface out of the compaction zone. Whether a
     run compacts follows how many landblocks it loads. The surface cannot
     show q5pacs's heap saving: the live-heap fits put every run at
     6.3-7.3 GB at 7,000 landblocks. C.7 measures it on the dungeon load.

C.7  The memory fixes and R.2 on the dungeon load (runs 23-30)

     steady, and what does the second memory set (q5pacsm2) add on top?
     And does R.2's lock-free landblock lookup still pay once q5pa has

     beyond the noise in both halves.

     and the large object heaps (GCHIST). On base it matches the forced
     full GCs of the diagnostic run (5.75-5.94 GB, D.11).
     RUN 23 (q5pa): 1.435 cores, 165 MB/s, 24.9 collections a minute at
     37.2 ms each, against 1.449 and 1.452 cores, 165-166 MB/s and 37 ms

Detail and evidence for D.1-D.5 are in perf-physics.txt Section S.

D.1  On the surface one landblock group holds 3,756-5,345 of the ~5,500-6,800
     loaded landblocks. The server manages 39 updates a second on 1.45 of 8
     cores: world update 25.1 ms against a 16.7 ms budget. (S.1)
D.2  When the working set reaches ~12.5 GB, the GC does a blocking compacting
     gen2 that stops the world for 1.3-4.3 s, up to eight times in 45 min. The
     dungeon load never got there. On a surface run that loaded ~10% more
     landblocks (run 11) they chained: up to 5 blocking gen2s in 15 s, 8.3 s
     of pause, and a 10.9 s world update. In the .NET 10 GC source the
     trigger is free memory, not process size: at 90% memory load
     (MemAvailable under ~1.6 GB here) a gen1 or older collection may turn
     into a blocking compacting gen2. Run 20's GC events confirm it: its 3
     blocking gen2s all started at 90% load, and none of its 231 gen1s at
     71-89% became one. Run 21 peaked at 85% and had none. Run 22's 2
     started at 91% and 90%, and 341 of its 342 gen1s were below 90%. (S.2)
D.3  The process memory is the GC heap: ~6.5-7.5 GB of live objects plus
     1-5.7 GB of gen2 free space. Native memory outside it is ~0.1 GB. (S.3)
D.4  Each young GC stops the world for ~25 ms, one ~530 MB of allocation
     apart: about one lost tick per collection. Of a 22 ms gen0 pause, 8 ms
     is card marking and 13 ms is relocating and compacting the survivors;
     stacks cost 0.35 ms. Nearly all survivors are reached from old objects.
     About 10 MB/s (dungeons) to 27 MB/s (surface) is promoted into gen2 and
     dies there, which is the gen2 free space of D.3. (S.4)
D.5  "[PERFORMANCE][PHYSICS] ... took N ms" log lines under load are GC
     pauses, not slow objects. (S.5)
D.6  DATAS off, dungeon load: 7% more cores, three times the collections,
     3.8% of the time paused instead of 2.2%. On the surface it reached
     13.46 GB and was stopped short of running out of memory. DATAS stays on
     until the GC-setting phase.

D.11 The live heap on the dungeon load is 5.75-5.93 GB, flat after 40 min.
     About 2.7 GB of it is copies of the same cell geometry: every EnvCell
     builds its own CellStruct, 134,117 of them from 958 distinct dat
     structures (about 140 each), with 21.8 million Vertex objects. Smaller
     items: VisibleCells dictionaries 0.4 GB; 12 empty cache dictionaries on
     every WorldObject, 0.2 GB; a GUID recycle queue that holds every
     destroyed object's GUID for 6 hours (1.24 -> 3.77 million entries in
     40 min). (S.7) On q5pacs, which shares the geometry, 2.97-3.10 GB
     survive each background gen2 (C.7, run 24); on q5pacsm2, 2.50-2.57 GB
     (run 25).
D.12 In three of the four base surface runs the GC collected every 160 MB
     allocated for most of the window, against ~530 MB on the dungeon load
     and 500-540 MB on the pg1, pg1r2 and q5pa surface runs and the fourth
     base run. CAUSE: the .NET GC trims the gen0
     budget by memory load (gc.cpp joined_youngest_desired). After each
     blocking collection it caps the total budget at (85 - load)% of RAM,
     and at 1% of RAM (161 MB here) from 84% up. Per heap that is 67.1 MB
     (DATAS's 64 MiB cap) up to 81% load, then 60.7, 40.4 and 20.2 MB:
     exactly the values in the GC's events. On this VM the full budget
     needs ~2.9 GB of MemAvailable, and below ~2.6 GB it is 160 MB. The
     three trimmed base surface runs follow it minute by minute, and go back to
     ~520 MB whenever a blocking gen2 frees memory. pg1, pg1r2 and q5pa
     kept the large budget at 84-90% load. That is DATAS's state, not the
     build (gcpriv.h compute_gen0_budget_per_heap). Once DATAS's last
     tuning step has changed the budget, it only scales the previous
     budget by 98 / (100 - GC time %) after each GC, so the budget stays
     high while GC time is near its 2% target. After a heap-count change,
     any interval under 2% puts it back to the trimmed value. DATAS's own
     events in the GC traces show both: run 20 changed its heap count at
     12.7 min, sat at the trimmed 48 MB per heap (83% load) for 13 min,
     then made a budget step and held 63-67 MB at 84-90%. Run 21 made a
     budget step at 6 min and held 67 MB at 84-85%. Run 22 (base) made
     budget steps at 1 and 6.5 min and held 66-67 MB at 82-91%, so base is
     not trimmed by nature. The 85% is a constant
     in gc.cpp, not a setting.
     CONSEQUENCE: on the surface the collection count follows free memory,
     so compare builds by total pause and worst pause. Below ~2.9 GB free,
     each MB taken off the heap also lengthens the gen0 budget. (S.4)
D.13 What base allocates on the surface (run 13, 30 s sample): 55% under
