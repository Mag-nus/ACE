SECTION B - PER-HIT AND PER-READ WASTE
================================================================================

O.3  Enum.Parse plus string concatenation on every landed hit
     Player_Combat.cs:174, 545; Monster_Combat.cs:323, 410

         (PlayScript)Enum.Parse(typeof(PlayScript),
                                "Splatter" + GetSplatterHeight() + GetSplatterDir(target))

     Runs TWICE per landed melee or missile hit (attacker and defender side),
     plus `"Wound" + rng` when damage is at least 25% of health. That is a
     reflection-based parse (microseconds) plus three string allocations, where
     a static PlayScript[4,3] lookup keyed by (AttackHeight, Quadrant) would be
     O(1) and allocation-free.

     HIGHEST RATIO OF COST TO FIX DIFFICULTY IN THIS DIRECTORY.

O.4  Skill and attribute Current fully recomputed on every read
     WorldObjects/Entity/CreatureSkill.cs:154-195;
     Entity/CreatureAttribute.cs:141-155

     One Current read = the attribute formula (which itself recomputes
     attributes) + GetAugBonus_Base (4+ locked property reads and 3
     HashSet.Contains) + Vitae + two enchantment lookups.

     GetCreatureSkill(...) appears 32 times across the combat partials; a single
     attack resolves attack skill, defense skill, shield skill and dirty-fighting
     checks. CreatureAttribute.GetCurrent also evaluates Base TWICE (lines 146
     and 152) where one local would do.

     FIX: memoise Current with a dirty flag set by enchantment and attribute
     changes; at minimum hoist to locals in GetEffectiveDefenseSkill
     (Creature_Combat.cs:481-500).

O.5  Expensive properties evaluated inside loops
     Creature_Networking.cs:251-254 references wo.CSetup THREE TIMES per
     iteration over ~50 parts. CSetup (WorldObject_Properties.cs:947) is a
     locked SetupTableId read plus a DatManager.PortalDat.ReadFromDat
     concurrent-dictionary lookup. Line 230 in the same file does it correctly
     with a local - so the fix pattern is adjacent.
     Same shape: WeenieClassName (WorldObject_Properties.cs:1161-1172) calls
     GetCachedWeenie twice.
     Per appearance recalculation (equip change, object create), not per tick.


SECTION C - ENCHANTMENTS
================================================================================

O.6  Top-layer queries: no per-tick memo, group-by plus triple OrderByDescending
     per miss
     Managers/EnchantmentManager.cs:118-129 ->
     ACE.Entity/Models/PropertiesEnchantmentRegistryExtensions.cs:168-247

     Each cache miss costs a read lock, a Where, a `group by SpellCategory`, an
     `OrderByDescending(PowerLevel).ThenByDescending(HashSet.Contains).ThenByDescending(...)`
     and a .ToList() - roughly 6 allocations and an O(n log n) sort, usually to
     pick a single element.

     EnchantmentManagerWithCaching (used by all WorldObjects, WorldObject.cs:251)
     memoises about 20 accessors - but ClearCache() WIPES ALL CACHES on any
     Add, Remove, Dispel or StartCooldown
     (EnchantmentManagerWithCaching.cs:169-203). In sustained combat - DoTs,
     procs, buffs expiring each heartbeat - the whole cache is dumped repeatedly
     and every subsequent stat read re-sorts.

     Uncached entirely: GetModifier, GetAdditiveMod, GetMultiplicativeMod,
     GetDamageOverTimeMod, GetAttackDebuffMod, GetDefenseDebuffMod.

     FIX: replace the group-and-sort with a single-pass max-per-category scan
     (no LINQ, no intermediate list), and make invalidation GRANULAR - only the
     affected StatModKey rather than everything.

     NOTE: bugs-entity-shared.txt S.3 reports that this same registry mutates
     under a READ lock during the heartbeat. Fix that first - it is a data race -
     then optimise here.

SECTION E - RECONCILIATION: BROADCAST AMPLIFICATION
================================================================================
[VERIFIED DIRECTLY - two audits appeared to disagree; both are correct]

This audit found that EnqueueBroadcast does NOT rebuild the message per
recipient. perf-network.txt P.1 found that object creation DOES. I read both
call sites; they are different paths and both reports are accurate.

  SHARED (correct, no amplification):
    WorldObject_Networking.cs:1376
      `EnqueueBroadcast(GameMessage msg, float range, ...)` takes ONE message
      and enqueues that SAME INSTANCE inside the recipient foreach. Confirmed.
      This covers ongoing position, motion and effect broadcasts.

  PER-RECIPIENT (the amplification):
    Player_Tracking.cs:62
      `Session.Network.EnqueueSend(new GameMessageCreateObject(worldObject,
                                   Adminvision, Adminvision));`
      constructs a NEW message per observing player. Confirmed. This covers
      object creation - i.e. zone entry - and drags CalculateObjDesc with it.

  CONCLUSION: ongoing broadcasts are fine; ZONE ENTRY is O(N^2). Fix the
  creation path (perf-network.txt P.1), not the broadcast path.

  STILL WORTH FIXING on the broadcast path: each EnqueueBroadcast allocates a
  `params GameMessage[]` and a fresh List<Player> via
  `KnownPlayers.Values.Select().OfType<Player>().ToList()` under a lock
  (ObjectMaint.cs:717-728), called for every moving monster at ~5Hz and every
  player position broadcast. EnqueueBroadcast(excludePlayers, ...) at line 1456
  adds an .Except() that builds a HashSet per call.
  FIX: a cached or pooled known-player list invalidated on visibility change,
  plus non-params overloads for 1-2 messages. (Same finding as
  perf-network.txt P.9 and perf-entity-server.txt E.3 - three audits found it
  independently, which is good evidence it is real.)

--- P: HIGH IMPACT ---

P.1  Every projectile allocates a full Biota plus a manager set
     WorldObject_Magic.cs:1774, Creature_Missile.cs:92 ->
     WorldObject.cs:104-116, 246-258

     Each spell projectile or arrow calls
     WorldObjectFactory.CreateNewWorldObject, which runs
     WeenieConverter.ConvertToBiota (WeenieConverter.cs:13-92: up to EIGHT
     fresh Dictionary copies plus cloned position/animpart/palette lists), and
     then SetEphemeralValues allocates an EmoteManager, an
     EnchantmentManagerWithCaching, a SequenceManager, a Motion, a PhysicsObj,
     2-3 Position clones, and a GuidManager.NewDynamicGuid().

     A war-magic blast is 5-8 of these PER CAST, and all of them are destroyed
     roughly 5 seconds later (SpellProjectile.cs:240-243).

     FIX: pool projectile WorldObjects per wcid; or make the projectile biota
     reference the weenie's dictionaries copy-on-write - note
     `referenceWeenieCollectionsForCommonProperties` already exists for a
     subset - and construct EmoteManager/EnchantmentManager lazily on first
     use.

     This is the single largest allocation source found in this directory, and
     it lands on the landblock worker threads (see the closing note of
     perf-factories.txt for why that placement matters).

P.2  GameMessageCreateObject is rebuilt per recipient, and creature ObjDesc is
     recomputed every time
     Player_Tracking.cs:62, WorldObject_Networking.cs:56, 223,
     Creature_Networking.cs:35-243

     Each player gaining visibility of an object constructs its OWN message
     (PhysicsObj.cs:2295-2350 calls player.TrackObject per player).
     Serialisation runs CalculateObjDesc() - for creatures that is three LINQ
     chains with Where/OrderBy/Concat/ToList over equipped items,
     setVisualClothingPriority per item, dat lookups per item, plus a
     List<uint> coverage with O(n) Contains - followed by
     CalculateWeenieHeaderFlag, Flag2 and UpdateObjectDescriptionFlags.

     Together that is roughly 100 LOCKED BIOTA PROPERTY READS, repeated PER
     RECIPIENT.

     FIX: cache ObjDesc on the creature and cache the serialised CreateObject
     byte buffer, reusing it for all non-adminvision recipients.

     *** INVALIDATION SET RESOLVED - THE ORIGINAL LIST WAS INCOMPLETE ***
     [VERIFIED DIRECTLY by reading both CalculateObjDesc implementations]

     An earlier version said "invalidated on equip/dye/cloak/barber". That
     misses at least two categories. The actual input surface is:

       BASE - WorldObject_Networking.CalculateObjDesc:906-990 reads:
           ClothingBase, HeadObjectDID, PaletteTemplate, SetupTableId, Shade

       CREATURE - Creature_Networking.CalculateObjDesc:35-120 additionally
       reads EquippedObjects (filtered on ItemType and CurrentWieldedLocation)
       and, PER EQUIPPED ITEM, TopLayerPriority and VisualClothingPriority -
       plus SetupTableId again.

     So the invalidation set must include:
       1. Equip / unequip                    (EquippedObjects membership)
       2. Barber                             (HeadObjectDID, PaletteTemplate,
                                              Shade on the creature)
       3. Cloak status toggle
       4. Dye applied to the CREATURE        (PaletteTemplate, Shade)
       5. *** Dye or any visual-property change applied to an EQUIPPED ITEM ***
          - ClothingBase, PaletteTemplate, Shade, TopLayerPriority and
            VisualClothingPriority all belong to the ITEM, and a change on a
            worn item changes the WEARER's ObjDesc. An item-level invalidation
            must propagate to its wielder. This was missing entirely.
       6. *** SetupTableId changes on the creature ***
          - i.e. @morph (AdminCommands.cs:3591), gear-knight and olthoi-play
            form changes, and any transform. This was also missing, and it is
            the most visible failure mode: a morphed creature would keep
            rendering its OLD model for every observer until something
            unrelated invalidated the cache.
       7. Any admin command that sets these properties directly.

     IMPLEMENTATION NOTE: given categories 5 and 6, a property-version stamp
     on the biota is a more robust trigger than an enumerated hook list - the
     enumeration is exactly what went wrong here, and item-level changes make
     the hook list cross-object.

     This confirms and sharpens perf-network.txt P.1 from the gameplay side -
     the O(N^2)-on-zone-entry problem is not just message construction, it is
     ~100 lock acquisitions per recipient inside it.

P.3  Spell-component inventory walks, 10-16 times per cast
     Player_Magic.cs:1227-1246 and 1203, via Container.cs:312-335

     HasComponentsForSpell calls GetNumInventoryItemsOfWCID once per required
     component (typically 4-8), and TryBurnComponents calls
     GetInventoryItemsOfWCID again per burned component. Each call RECURSIVELY
     WALKS the main pack and every side pack, allocating
     `Where(...).OrderBy(...).ToList()` per container level.

     That is roughly 10-16 full inventory-tree walks WITH SORTS per cast, per
     casting player.

     FIX: one pass that counts all required wcids into the GetRequiredComps()
     dictionary; or a maintained wcid -> items index on the player, updated in
     TryAddToInventory / TryRemoveFromInventory.

P.4  Per-recipient biota read inside every broadcast loop
     WorldObject_Networking.cs:1391-1407, 1434-1441, 1455-1462, 1049-1058,
     1355-1368

     `Visibility` (WorldObject_Properties.cs:2410 -> Biota.GetProperty under
     BiotaDatabaseLock, a ReaderWriterLockSlim) is read INSIDE the recipient
     loop. A broadcast to 40 known players therefore takes 40 lock acquisitions
     on the SENDER's biota. `isDungeon` is likewise loop-invariant.

     There are 225 broadcast call sites in this directory.

     FIX: hoist Visibility, self and squelch state above the loop; add a cached
     recipient array on ObjMaint invalidated on known-player add/remove.

     The recipient-list allocation half of this was already reported (pass 1
     Section E, perf-network.txt P.9, perf-physics.txt F.2). The PER-RECIPIENT
     PROPERTY READ is the new part, and it compounds the lock-cost analysis in
     perf-entity-shared.txt E.1.

P.5  [VERIFIED DIRECTLY] Monsters broadcast UpdatePosition UNCONDITIONALLY at
     5Hz, while players are throttled
     Monster_Navigation.cs:255-263, versus Player_Tick.cs:403, 513

     Monster_Navigation.UpdatePosition ends with:

         if (netsend)
             SendUpdatePosition();

     with NO movement threshold and NO dedupe. Players, by contrast, are
     explicitly throttled at Player_Tick.cs:513:

         if (RequestedLocationBroadcast ||
             DateTime.UtcNow - LastUpdatePosition >= MoveToState_UpdatePosition_Threshold)

     with MoveToState_UpdatePosition_Threshold = 1 second (line 403).

     So every moving or returning monster sends a full GameMessageUpdatePosition
     to all known players every 200ms - a 5x higher rate per monster than per
     player. With a large pull this is the main outbound packet source, and it
     feeds directly into the per-recipient fragment copy in perf-network.txt
     P.2.

     FIX: skip the send when the position delta is below an epsilon and
     velocity is unchanged; otherwise rate-limit as players already are. The
     mechanism exists in-tree.

P.11 Unconditional Stopwatch instrumentation on the 60Hz object path
     WorldObject_Tick.cs:290, 372; Player_Tick.cs:296, 323, 429, 527

     PROCESS-GLOBAL LOCK hit from all parallel landblock worker threads.
     FIX: gate the stopwatch behind the same IsRunningCumulative flag; make the
     accumulator thread-local and sum at report time.
     NOTE: perf-managers.txt P.3 reports the same instrumentation problem from

     (Pass 1 Section F.8 assessed WorldObject.UpdateObjectPhysics as correctly

*** THE ANSWER TO THE OPEN QUESTION: ARE DERIVED COMBAT VALUES CACHED? ***
Mixed - and the pattern of what IS cached shows the codebase already knows how.

  CACHED CORRECTLY
    Enchantment-derived armor mod, ArmorModVsType, ratings, skill/attribute/
    vital mods, attack/defense/damage/variance mods
        -> EnchantmentManagerWithCaching, on every WorldObject
           (WorldObject.cs:251)
    Equipped-item gear rating sums (GearDamage, GearCrit, GearMaxHealth, ...)
        -> INCREMENTAL dictionary maintained on equip/unequip, NO O(n) scan
           (Creature_Equipment.cs:213-276). This is the correct pattern and it
           already exists in the file that needs it most.
    Max spell level for armor cleaving -> lazy (WorldObject_Magic.cs:1950)

  NOT CACHED
    Armor level totals across pieces  -> full LINQ rescan per attack
    Resistance / protection per piece -> only the enchantment delta is cached
    Attack / defense / shield skill   -> CreatureSkill.Current fully recomputed
    Max health / stamina / mana       -> recomputed per read
    Damage/crit/crit-dmg/DRR ratings  -> inputs cached, but the SUM is
                                         recomposed and pulls 1-3 UNCACHED
                                         Biota aug reads each

  CHEAP, LEAVE ALONE
    CreatureAttribute.Current - reads propertiesAttribute fields directly, no
    Biota lock (CreatureAttribute.cs:386-400).

Q.13 Countdown properties dirty the biota of every decaying object and every
     generator on a timer
     WorldObject_Decay.cs:86, WorldObject_Tick.cs:117 and :131, with
     ACE.Entity/Enum/Properties/PropertyFloat.cs

     *** CORRECTED - AN EARLIER VERSION OF THIS ENTRY RECOMMENDED A FIX THAT
         WOULD HAVE BROKEN GAMEPLAY. THE CORRECTION IS THE IMPORTANT PART. ***

     THE OBSERVATION (still valid):
     `TimeToRot -= elapsed` (WorldObject_Decay.cs:86) -> SetProperty ->
     ChangesDetected = true on EVERY decaying object EVERY landblock heartbeat
     (Entity/Landblock.cs:525-529). The generator timestamps do the same on
     every generator in every loaded landblock every 5 seconds
     (Landblock.cs:474-490). Landblock.SaveDB (Landblock.cs:1179-1205) then
     rewrites them every save cycle, on the single serialized shard thread.

     The enum state, which is accurate:
         [Ephemeral]
         HeartbeatTimestamp             = 2,     <-- IS ephemeral
         RegenerationTimestamp          = 42,    <-- is NOT
         TimeToRot                      = 44,    <-- is NOT
         GeneratorUpdateTimestamp       = 113,   <-- is NOT

     THE WRONG RECOMMENDATION (retracted): "mark all three [Ephemeral] - the
     mechanism already exists - provably safe."

     WHY IT WAS WRONG: [Ephemeral] means the property does NOT need to be
     restored after a server restart. That is exactly backwards for TimeToRot,
     which is REMAINING ROT TIME. Marking it ephemeral resets every corpse's and
     every dropped item's decay countdown on every restart - so on a shard that
     restarts regularly, items would never decay at all. That is a gameplay
     regression, and it was rated "provably safe", which compounded the error.

     WHAT IS ACTUALLY TRUE, PER PROPERTY (verified by reading the call sites):

       TimeToRot - MUST PERSIST. It is a countdown whose whole purpose is to
         survive a restart so decay completes after the correct elapsed game
         time. Do not make it ephemeral.

       RegenerationTimestamp - MUST PERSIST, and for a non-obvious reason. The
         only functional read is GetNextRegenerationTime
         (WorldObject_Generators.cs:498-503), which tests `== 0` to distinguish
         "never regenerated" from "has regenerated before": zero returns
         Time.GetUnixTime() (spawn now), non-zero applies generatorInitialDelay.
         Making it ephemeral would make EVERY generator look fresh after a
         restart and fire immediately, skipping its initial delay. That is a
         behaviour change, not a no-op.

       GeneratorUpdateTimestamp - has NO functional reads anywhere. The only
         consumers are the property accessor and a developer command display
         (Command/Handlers/DeveloperCommands.cs:2766). This is the one of the
         three with a genuine case for being ephemeral - but the payoff is the
         smallest of the three, and the only cost of getting it wrong is a
         confusing @ command readout, so it is not worth much risk either.

     THE REAL LEVER, IF ANY: the data genuinely needs to persist, so the only
     available saving is WRITE CADENCE, not write elimination. Keep the live
     countdown in a plain field and write it through to the biota periodically
     and on landblock unload, rather than marking the biota dirty every
     heartbeat. The tradeoff is explicit: an unclean shutdown loses up to one
     write-interval of decay progress. That is a judgement call for the shard
     operator, not a free win.

     REVISED SEVERITY: LOW-to-MEDIUM, and NOT the highest-value item in this
     section. The write amplification is real, but it is amplification of data
     that legitimately must be stored, so the ceiling on any fix is much lower
     than first claimed.

     LESSON FOR THE REST OF THIS DOCUMENT SET: "this property is written often
     and rarely read" is NOT sufficient grounds to stop persisting it. Check
     what depends on it ACROSS A RESTART before proposing to drop it - the read
     may be a single `== 0` test, as with RegenerationTimestamp, and still be
     load-bearing.
