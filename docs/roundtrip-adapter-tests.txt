--------------------------------------------------------------------------------
1. METHOD
--------------------------------------------------------------------------------
Two complementary techniques.

(a) GENERIC REFLECTION SWEEP. For each round-trippable pair, build an ACE-side
    object with every scalar member set to a distinctive non-default value and
    every collection populated, convert ACE -> external -> ACE, then structurally
    diff the start and end graphs by reflection and report every differing path.
    Run twice: once with all booleans seeded true, once false. That second pass
    is what exposes polarity inversions, which a single pass can hide.

(b) TARGETED PROBES. One concrete semantic assertion each, for defects the
    generic sweep pointed at. These are the high-confidence results.

CRITICAL TECHNIQUE NOTE - WITHOUT THIS THE SUITE FINDS ALMOST NOTHING.
Every converter wraps its body in a bare `catch { return false; }`. Failures are
therefore SILENT: the caller sees `false` with no message, no exception, no log.
The harness installs an AppDomain.FirstChanceException handler to observe
exceptions the converters swallow. Every stack trace quoted below was recovered
that way. Reading `return false` tells you nothing about WHY.

3. FINDINGS
--------------------------------------------------------------------------------

RT.1 [HIGH] A weenie with a PARTIAL attribute set is silently discarded whole
     Lifestoned/LifestonedConverter.cs:548 (guard), 558-600 (the dereferences)

     OBSERVED OUTPUT:
         weenie with Strength only        : TryConvert returned False
           -> WEENIE SILENTLY DROPPED (exception swallowed by bare catch)
         control, all six attributes      : TryConvert returned True
         swallowed: NullReferenceException at LifestonedConverter.cs:573

     The guard admits any weenie with at least one attribute:
         if (input.WeeniePropertiesAttribute != null
             && input.WeeniePropertiesAttribute.Count > 0)
     Inside, all SIX attributes are read like this - three times each, and
     WITHOUT a null check on the FirstOrDefault result:
         Ranks = input.WeeniePropertiesAttribute
                     .FirstOrDefault(a => a.Type == (ushort)PropertyAttribute.Endurance)
                     .InitLevel
     FirstOrDefault returns null when that attribute is absent, so `.InitLevel`
     throws. The bare catch turns that into `return false`, and the ENTIRE
     WEENIE is dropped - not just its attributes.

     WHY THIS MATTERS: "Count > 0" is not "has all six". Any weenie carrying an
     incomplete attribute set - which the schema permits, since these are
     individual property rows - is unexportable, and the tooling reports only a
     bare false.

     FIX: hoist one lookup per attribute and null-check it, e.g.
         var end = input.WeeniePropertiesAttribute
                       .FirstOrDefault(a => a.Type == (ushort)PropertyAttribute.Endurance);
         if (end != null)
             result.Attributes.Endurance = new GDLE.Models.Attribute
             { Ranks = end.InitLevel, LevelFromCp = end.LevelFromCP, XpSpent = end.CPSpent };
     This also removes 18 redundant LINQ scans (6 attributes x 3 reads).

RT.2 [HIGH] GDLE recipe import dereferences input.Requirements without a null check
     GDLE/GDLEConverter.cs:781                            *** NOT PREVIOUSLY DOCUMENTED ***

     OBSERVED OUTPUT:
         Requirements=null, Mods.Count=0 -> returned False
           swallowed: NullReferenceException at GDLEConverter.cs:781

     Line 781 is `foreach (var value in input.Requirements)`. There IS a null
     check one line later - `if (value == null) continue;` - guarding the
     ELEMENTS, but nothing guards the COLLECTION.

     FAILURE: any GDLE recipe JSON that omits the `Requirements` array
     deserialises to null and the whole recipe is silently dropped on import.

     THIS MASKS RT.3. Line 781 executes before the Mods loop at 877, so on
     minimal JSON you hit this NRE and never reach the documented Mods defect.
     That is why the Mods issue only reproduces once Requirements is non-null.

     FIX: `if (input.Requirements != null) foreach (...)`, or initialise the
     property to an empty list in Models/Recipe.cs:84 as Mod.cs already does
     for its own collections.

RT.3 [HIGH] Mods indexed 0..7 unconditionally - CONFIRMS DOCUMENTED A.7
     GDLE/GDLEConverter.cs:877-884

     A.7 was previously traced but not verified. It is now EMPIRICALLY CONFIRMED,
     and the boundary is exactly as predicted. Holding Requirements non-null to
     get past RT.2 and varying only Mods.Count:

         Mods.Count=0  -> TryConvert returned False   *** recipe dropped ***
             ArgumentOutOfRangeException: Index was out of range
         Mods.Count=1  -> TryConvert returned False   *** recipe dropped ***
         Mods.Count=7  -> TryConvert returned False   *** recipe dropped ***
         Mods.Count=8  -> TryConvert returned True
         Mods.Count=9  -> TryConvert returned True
         Mods=null     -> TryConvert returned False
             NullReferenceException at GDLEConverter.cs:881

     So: fewer than 8 throws, exactly 8 or more succeeds, null throws a
     different exception a few lines further on. The loop is
     `for (int i = 0; i < 8; i++) // Must be 8` and the `value == null` check
     sits AFTER `input.Mods[i]`, so it cannot help.

     FIX (as documented in A.7):
         if (input.Mods == null || i >= input.Mods.Count) continue;

RT.4 [HIGH] Cookbook export REPORTS SUCCESS while silently dropping the recipe
     GDLE/GDLEConverter.cs:421 and :436

     OBSERVED OUTPUT:
         [minimal valid recipe]
           forward returned True; combined.recipe is populated; precursors=1
           reverse returned True
         [recipe that fails export]
           forward returned True; combined.recipe is NULL; precursors=1
           *** REPORTS SUCCESS WHILE SILENTLY DROPPING THE ENTIRE RECIPE ***
           reverse returned False
             NullReferenceException at GDLEConverter.cs:747

     Line 421 discards the result of the inner conversion:
         TryConvert(recipe, out var newRecipe);      // return value IGNORED
         if (newRecipe != null)
             newRecipe.RecipeId = 0;
         result.recipe = newRecipe;                  // may be null
     ...and line 436 unconditionally `return true`. The null check protects the
     RecipeId assignment but not the caller's understanding of the outcome.

     CONSEQUENCE, OBSERVED AS A TWO-STAGE CASCADE: the export writes a
     RecipeCombined whose `recipe` is null and calls it success. Re-importing
     that object then NREs at line 747 dereferencing `input.RecipeId`. A failure
     originating in the recipe converter surfaces as a crash in an unrelated
     later operation, with the true cause already discarded.

     FIX: honour the bool.
         if (!TryConvert(recipe, out var newRecipe)) { result = null; return false; }

RT.5 [MEDIUM] Cookbook export has no try/catch and dereferences an EF navigation
     GDLE/GDLEConverter.cs:414-418

     Alone among the converters, `TryConvert(List<CookBook>, out RecipeCombined)`
     has NO try/catch. It guards the list:
         if (cookbooks == null || cookbooks.Count == 0) { result = null; return false; }
     then immediately does:
         var recipe = cookbooks[0].Recipe;   // navigation property
         result.key = recipe.Id;             // unguarded dereference

     OBSERVED: with `Recipe` not populated, this threw NullReferenceException
     that ESCAPED to the caller (GDLEConverter.cs:418) rather than returning
     false. The harness had to wire the navigation property explicitly to reach
     the real code path.

     CAVEAT ON SEVERITY - INFERRED, NOT OBSERVED IN PRODUCTION: whether a real
     caller can hit this depends on whether `CookBook.Recipe` is eager-loaded at
     every call site. I did not audit the callers. The defensive point stands
     regardless: this is the one converter whose failure mode is an escaping
     exception instead of `false`.

     FIX: null-check `recipe`, and wrap the body to match its siblings.

RT.6 [LOW] LandblockInstance.IsLinkChild is dropped on import
     GDLE/GDLEConverter.cs:127-210

     OBSERVED: `[0].IsLinkChild: True -> False` in the boolean-true pass only.
     `IsLinkChild` appears NOWHERE in GDLEConverter.cs - it is simply never
     assigned on the import side, so it defaults to false.

     CAVEAT: this may be intentional if ACE recomputes the flag when links are
     inserted, since links arrive via the separate `out links` parameter.
     VERIFY BEFORE FIXING - I did not trace the DB insert path.

4. CONFIRMATION OF A.6 (the book-page permission bug)
--------------------------------------------------------------------------------
A.6 was previously established by reading. It is now EMPIRICALLY CONFIRMED, and
the observed behaviour is worse than "round trips flip it": it inverts in BOTH
directions on a SINGLE pass.

     OBSERVED OUTPUT:
         IgnoreAuthor True  -> wire byte 1 -> False   *** FLIPPED ***
         IgnoreAuthor False -> wire byte 0 -> True    *** FLIPPED ***

Note the middle column - the wire byte is CORRECT in both cases. The setter
writes 1 for true and 0 for false, exactly as expected. The getter then misreads
it. This isolates the defect to the getter alone and directly supports the
"fix the getter, not the setter" conclusion in A.6.

The second line is the security-relevant one. `IgnoreAuthor == true` means
"skip the author check - anyone may edit or delete this page" (Book.cs:137,
Book.cs:155). An author-locked page (`false`) imports as world-editable
(`true`). That is now a measured result, not an argument.

--------------------------------------------------------------------------------
6. THE SYSTEMIC FINDING
--------------------------------------------------------------------------------
Individually the above are six defects. Together they are one problem:

    EVERY FAILURE MODE IN THIS SUBSYSTEM IS SILENT.

Each converter ends in `catch { return false; }` with no logging, no exception
detail, no indication of which field or record failed. Consequences observed
directly in this run:
  - RT.1 discards an entire weenie and reports only `false`;
  - RT.2 masks RT.3 completely, so the documented defect looks unreproducible;
  - RT.4 reports SUCCESS on a partial result, and the resulting crash surfaces
    in a different method with the original cause already gone.

Recommendation, ranked above any individual fix above: give the converters a
diagnostic channel - at minimum log the exception and the identifying key
(ClassId / RecipeId / landblock) in each catch. Content pipelines that fail
silently produce databases that are quietly wrong, which is exactly the failure
mode the Section A findings in bugs-adapter.txt keep describing.

--------------------------------------------------------------------------------
7. LIMITATIONS - READ BEFORE CITING THESE RESULTS
--------------------------------------------------------------------------------
1. SYNTHETIC INPUT. Objects are reflection-populated, not loaded from a real
   world database. Values are valid-shaped but not realistic. A real corpus
   would likely surface more, and would also rule out any harness artifacts I
   have misclassified in section 5.
2. THE THREE ONE-WAY CONVERTERS ARE UNTESTED (section 2). This suite cannot
   reach them.
3. NO JSON LAYER. Tests exercise object-to-object conversion. The
   serialise/deserialise round trip through GDLELoader / LifestonedLoader is not
   covered, so JSON-shape defects (missing property names, casing, converters)
   would not appear here.
4. COLLECTIONS HELD AT 2 ELEMENTS and recursion capped at depth 4, to keep the
   diff readable. Deeper or wider structures are not explored.
5. RT.5's real-world reachability is INFERRED, not measured - see its caveat.
6. Nothing in the ACE source tree was modified to produce these results.
