--------------------------------------------------------------------------------
1. METHOD
--------------------------------------------------------------------------------
Two complementary techniques.

(a) GENERIC REFLECTION SWEEP. For each round-trippable pair, build an ACE-side
    object with every scalar member set to a distinctive non-default value and
    every collection populated, convert ACE -> external -> ACE, then structurally
    diff the start and end graphs by reflection and report every differing path.
    Run twice: once with all booleans seeded true, once false. That second pass
    is what exposes polarity inversions, which a single pass can hide.
    Doubles are seeded as N + 0.1, which float cannot represent exactly, so any
    narrowing to float shows up as a difference.

    Every difference the round trip is allowed to produce is listed in the test
    with a reason (section 4). Anything else fails.

(b) TARGETED PROBES. One concrete semantic assertion each, for defects the
    generic sweep pointed at or cannot reach (import-only behaviour, partial
    sets, the JSON layer). These are the high-confidence results.

CRITICAL TECHNIQUE NOTE - WITHOUT THIS THE SUITE FINDS ALMOST NOTHING.
Every converter wraps its body in a bare `catch { return false; }`. Failures are
therefore SILENT: the caller sees `false` with no message, no exception, no log.
The harness installs an AppDomain.FirstChanceException handler, scoped to the
test's thread, to observe exceptions the converters swallow. Every stack trace
quoted below was recovered that way.

SEEDING MUST BE SCHEMA-VALID. Random values make several converters throw for
reasons that are not defects. The sweep holds these to valid shapes:
  - recipe requirement Index 0-2, recipe mod slot 0-7, all typed rows on one
    mod share its slot, and ExecutesOnSuccess = (slot <= 3)
  - all six attributes and the three max vitals present (partial sets are
    covered by probes)
  - book PageId and emote action Order numbered 0..n
  - landblock instances given in-range GUIDs and a real parent/child link

3. FINDINGS
--------------------------------------------------------------------------------

RT.1 [HIGH] A weenie with a PARTIAL attribute or vital set is silently discarded
     Lifestoned/LifestonedConverter.cs:554 (guard), 559-629 (the dereferences)
     Same defect as bugs-adapter.txt A.12.

     OBSERVED OUTPUT:
         weenie with Strength only       : TryConvert returned False
           swallowed: NullReferenceException at LifestonedConverter.cs:566
         weenie with MaxHealth only      : TryConvert returned False
           swallowed: NullReferenceException at LifestonedConverter.cs:615

     The guard admits any weenie with at least one attribute:
         if (input.WeeniePropertiesAttribute != null
             && input.WeeniePropertiesAttribute.Count > 0)
     Inside, all SIX attributes are read like this - three times each, and
     WITHOUT a null check on the FirstOrDefault result:
         Ranks = input.WeeniePropertiesAttribute
                     .FirstOrDefault(a => a.Type == (ushort)PropertyAttribute.Endurance)
                     .InitLevel
     FirstOrDefault returns null when that attribute is absent, so `.InitLevel`
     throws. The bare catch turns that into `return false`, and the ENTIRE
     WEENIE is dropped - not just its attributes. The vitals block repeats the
     pattern for MaxHealth/MaxStamina/MaxMana, so doors and chests (MaxHealth
     only) cannot be exported.

     FIX: one lookup per attribute and vital, null when absent. The import side
     already skips null entries, so the round trip is then exact. This also
     removes 27 redundant LINQ scans (9 entries x 3 reads).

4. NON-FINDINGS - differences that are BY DESIGN
--------------------------------------------------------------------------------
Recorded explicitly so nobody "fixes" them. Each is listed in the test as an
allowed difference.

  RT.6 RETRACTED - LandblockInstance.IsLinkChild false after import
      GDLEConverter.TryConvert(Models.Landblock) never assigns it, but its
      caller GDLELoader.TryConvertLandblocks sets it from the links
      (GDLELoader.cs:174-176). Not a defect; matches bugs-adapter.txt I.8.

  Database keys and timestamps
      Id, LastModified, and the foreign keys ObjectId, EmoteId, RecipeId and
      RecipeModId are not part of either external format. With them excluded,
      Quest and CookBook round trip cleanly.

  Navigation properties carried separately
      CookBook.Recipe and Recipe.CookBook: a precursor carries only RecipeId,
      and the combined-recipe pair carries the recipe beside the cookbooks.
      Landblock links come back through the `out links` parameter. The harness
      reattaches both the way the database navigation would; once it does, the
      combined-recipe and landblock pairs show no link or recipe loss.

  Landblock.Landblock -> <null>
      Computed DB column (ObjCellId >> 16), deliberately not assigned:
        //result.Landblock = input.key; ACE uses a virtual column here of
        //(result.ObjCellId >> 16)

  Landblock GUID reassignment
      Out-of-range GUIDs are reassigned to 0x7LLLL000 upward and link endpoints
      follow them. Probed directly; behaves as documented.

  Weenie.ClassName
      Not in the Lifestoned format; import derives it from the WCID.

  Recipe mod ExecutesOnSuccess
      Encoded by slot (0-3 success, 4-7 failure), not carried as a field. With
      schema-valid seeding it round trips.

  Book page and emote action numbering
      Renumbered 0..n on export, so non-sequential source numbering is not
      preserved. Ordering is.

FORMAT GAPS - the external model has no member to carry the data:
  WeeniePropertiesAnimPart, WeeniePropertiesEventFilter,
  WeeniePropertiesPalette, WeeniePropertiesTextureMap      (LSDWeenie)
  RecipeRequirementsString.Message                         (bugs-adapter.txt G.2)

--------------------------------------------------------------------------------
5. THE SYSTEMIC FINDING
--------------------------------------------------------------------------------
Individually the above are separate defects. Together they point at one problem:

    EVERY FAILURE MODE IN THIS SUBSYSTEM IS SILENT.

Each converter ends in `catch { return false; }` with no logging, no exception
detail, no indication of which field or record failed. Consequence observed
directly in this run: RT.1 discards an entire weenie and reports only `false`.

Recommendation, ranked above any individual fix: give the converters a
diagnostic channel - at minimum log the exception and the identifying key
(ClassId / RecipeId / landblock) in each catch. Content pipelines that fail
silently produce databases that are quietly wrong, which is exactly the failure
mode the Section A findings in bugs-adapter.txt keep describing.

--------------------------------------------------------------------------------
6. LIMITATIONS - READ BEFORE CITING THESE RESULTS
--------------------------------------------------------------------------------
1. SYNTHETIC INPUT. Objects are reflection-populated, not loaded from a real
   world database. Values are valid-shaped but not realistic. A real corpus
   would likely surface more.
2. THE THREE ONE-WAY CONVERTERS ARE UNTESTED (section 2).
3. JSON LAYER BARELY COVERED. One probe takes a weenie through JSON and back.
   The other pairs are tested object-to-object only, so JSON-shape defects
   (missing property names, casing - bugs-adapter.txt A.5, A.14) would not
   appear here.
4. COLLECTIONS HELD AT 2 ELEMENTS and recursion capped at depth 4. Deeper or
   wider structures are not explored.
5. VALUE RANGES ARE SMALL. Seeded integers are small and positive, so sign and
   width defects (bugs-adapter.txt G.3, palette ids above 127) are not reached.
