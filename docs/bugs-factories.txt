FINDING FROM THE INITIAL SWEEP (folded in)

F.0a [HIGH] Division by zero produces NaN and halts ALL loot generation
     Tables/Cantrips/CantripChance.cs:268-284 (Rescale), driven from
     ScaleCantripLevels at 239-266

     Rescale computes `scalar = target / total` with no guard for total == 0,
     and ScaleCantripLevels always calls it unconditionally.

     REACHABLE IN PRACTICE: minor_cantrip_drop_rate, major_cantrip_drop_rate,
     epic_cantrip_drop_rate and legendary_cantrip_drop_rate are live
     PropertyManager double properties an admin can set at runtime. Setting all
     four to 0 is a plausible way to disable cantrip drops entirely.

     Then every entry's chance becomes 0, so total == 0, scalar becomes
     Infinity, and `entry.chance * scalar` (0 * Infinity) yields NaN for every
     table entry. ChanceTable<T>.Roll() (Entity/ChanceTable.cs:30-51) then
     accumulates NaN in total, every `rng < total` comparison is false, and the
     fallback `this.Last(i => i.chance > 0)` matches nothing - because NaN > 0
     is also false - and throws InvalidOperationException. That crashes cantrip
     rolling for EVERY loot generation on the shard.

     The codebase guards this exact hazard elsewhere - LootGenerationFactory.cs:576-577
     has `if (totalProbability == 0) return;` before dividing for clothing
     colour selection - confirming this is an oversight rather than intent.

     FIX: guard total == 0 in Rescale, mirroring the existing check.

RNG CONTRACT (verified by the audit)
  ACE.Common/ThreadSafeRandom.Next(int,int) calls random.Value.Next(min, max+1)
  and is therefore INCLUSIVE OF BOTH BOUNDS. All 20 `Next(0, X.Count ...)` call
  sites in Factories/ correctly use `- 1`, except PlayerFactoryEx.cs, which
  uses a plain System.Random (exclusive) and is therefore also correct.
  NO off-by-one RNG bugs were found. This was the primary hypothesis going in,
  and it did not hold - worth recording so it is not re-investigated.

F.1  Client-supplied chargen values used as raw dat indices with no validation
     PlayerFactory.cs:35, 52, 66, 96, 100, 135, 358

     Unvalidated indexing throughout:
         HeritageGroups[(uint)info.Heritage]
         heritageGroup.Genders[(int)info.Gender]
         sex.HairStyleList[(int)info.Appearance.HairStyle]

         sex.EyeColorList[...]

     Worse: GuidManager.NewPlayerGuid() at CharacterHandler.cs:119 has ALREADY

     appearance fields against the dat list counts up front, and allocate the

SECTION B - MEDIUM SEVERITY
================================================================================

F.2  RollInterval returns negative values, inverting the burden bonus
     Tables/QualityChance.cs:249

     When LootQualityMod causes early table entries to be skipped by
     `curChance >= LootQualityMod` (line 242), prevChance is taken from a
     SKIPPED entry and can exceed rng.

     FAILURE: tier 3, LootQualityMod = 0.9, chances [0.20, 0.50, 0.80, 1.00].
     Entries 0-2 are skipped; i=3 is selected with prevChance = 0.80. With
     rng = 0.05: interval = (0.05 - 0.80) / 0.20 = -3.75, so the method returns
     (1/12) * (-3.75 + 3) = -0.0625.

     MutateBurden (LootGenerationFactory.cs:652) then computes
     burdenMod = 1 - (-0.0625 * 0.75) = 1.047 - so HIGH-QUALITY profiles
     produce items HEAVIER than the base weenie. The `qualityInterval == 0.0f`
     guard at line 643 does not catch negatives. Occurs on roughly 20% of rolls
     against such profiles.

     FIX: `prevChance = Math.Max(prevChance, LootQualityMod)` and clamp the
     result to [0, 1].

F.3  qualityMod acts as a cliff rather than a scale
     Entity/ChanceTable.cs:44

     `if (rng < total && total >= qualityMod)` skips any entry whose CUMULATIVE
     total is below qualityMod.

     FAILURE: GearRatingChance.cs:36 rolls [(false, 0.75), (true, 0.25)]. For
     any profile with LootQualityMod > 0.75 the `false` outcome becomes
     UNREACHABLE, so 100% of tier-8 items receive a gear rating - a
     discontinuous jump from the intended 25%. The same applies at
     EquipmentSetChance.cs:50 (0.66 -> 100% equipment sets) and
     ArmorModVsTypeChance.cs:100.

     FIX: scale the weights by qualityMod - as CantripChance.ScaleCantripLevels
     does - instead of thresholding cumulative totals.

F.4  Missing null check on GetSpellLevels aborts the whole corpse's loot
     LootGenerationFactory_Spells.cs:102, 288

     SpellLevelProgression.GetSpellLevels returns null for unregistered spells.
     Line 102 does `spellLevels.Count != 8` and line 288
     `cantripLevels.Count != 4` with no null guard - while every sibling call
     site guards correctly (LootGenerationFactory_Caster.cs:110, _Gem.cs:82,
     _Spells.cs:370).

     FAILURE: adding a spell to ArmorSpells or SpellSelectionTable without
     adding it to a progression list gives a NullReferenceException that aborts
     the ENTIRE corpse's loot generation, not just that one spell. A content
     edit therefore silently produces empty corpses.

     FIX: `if (spellLevels == null || spellLevels.Count != 8) { log; continue; }`

F.5  Inconsistent Tier - 1 bounds checking
     LootGenerationFactory.cs:783 plus 8 further sites

     UNCLAMPED: coinRanges[profile.Tier - 1]; QualityChance.cs:187;
     LootGenerationFactory_Spells.cs:198; ArmorTypeChance.cs:125;
     SpellLevelChance.cs:92; CantripChance.cs:85, 147; ScrollLevelChance.cs:60;
     AetheriaChance.cs:57 (Tier - 5).
     CLAMPED in the same codebase: LootGenerationFactory.cs:435, 715;
     WorkmanshipChance.cs:85; GemMaterialChance.cs:94.

     TreasureDeath.Tier is unvalidated world-DB data.

     FAILURE: an imported treasure_death row with tier = 0 or 9 throws
     ArgumentOutOfRangeException on every kill using that profile.

     FIX: clamp Tier once at load, or apply Math.Clamp uniformly.

F.6  Index -1 reachable through /lootgen
     LootGenerationFactory_Aetheria.cs:29

     AetheriaChance.Roll_ItemMaxLevel returns 0 when profile.Tier < 5, and then
     IconOverlay_ItemMaxLevel[0 - 1] throws. Normal loot generation is safe
     because TryRollMundaneAddon gates on tier, but MutateItem
     (LootGenerationFactory.cs:1038-1041) calls MutateAetheria for whatever
     tier the developer command supplies.

     FAILURE: `/lootgen <aetheria wcid>` against a tier 1-4 profile throws
     ArgumentOutOfRangeException. Same shape at _Clothing.cs:367 for cloaks.

     FIX: return early when ItemMaxLevel <= 0.

F.7  Unvalidated min/max amount from the database
     LootGenerationFactory.cs:51, 65, 79

     `ThreadSafeRandom.Next(profile.ItemMinAmount, profile.ItemMaxAmount)`
     resolves to Random.Next(min, max+1), which throws when min > max.

     FAILURE: a treasure profile with item_Min_Amount = 2 and
     item_Max_Amount = 1 throws ArgumentOutOfRangeException - and because all
     three category blocks share one try/finally with NO catch, the corpse
     produces ZERO loot rather than skipping the one category.

     FIX: `Next(min, Math.Max(min, max))`.


SECTION C - LOW SEVERITY
================================================================================

F.8  Nullable comparison silently skips the legendary-cantrip level requirement
     LootGenerationFactory_Spells.cs:306, 309
     `wo.WieldDifficulty < 180` on an int?: when WieldDifficulty is null the
     comparison is FALSE in C#, so an item with WieldRequirements == Level but
     no difficulty set keeps a legendary cantrip with no level gate.
     SetWieldLevelReq (_Clothing.cs:300-310) handles the equivalent case
     explicitly.
     FIX: `(wo.WieldDifficulty ?? 0) < 180`.

F.9  Missing `> 0` guard clobbers cloak MaterialType
     LootGenerationFactory_Clothing.cs:394
     `wo.MaterialType = GetMaterialType(wo, profile.Tier)` runs
     unconditionally, whereas MutateArmor:48, MutateCaster:56,
     MutateMeleeWeapon:58 and MutateMissileWeapon:55 all guard
     `if (materialType > 0)`. GetDefaultMaterialType
     (LootGenerationFactory.cs:480-511) leaves material = MaterialType.Unknown
     for any WeenieType/ItemType combination its switch does not cover.
     FAILURE: a cloak weenie missing TsysMutationData has its authored
     MaterialType overwritten with 0, breaking salvage and appraisal.

F.10 Unbounded retry loop
     LootGenerationFactory_Scroll.cs:19-24
     `do { ... } while (spellId == SpellId.Undef)` has no attempt cap.
     ScrollSpells.AddSpells (ScrollSpells.cs:389-400) continues on a missing or
     malformed progression, leaving that pre-allocated row all-Undef. If a data
     change ever made every row Undef at the rolled level index, this spins
     forever on the loot thread with no logging. Compare RollEnchantments
     (_Spells.cs:139), which caps at numEnchantments * 3.
     FIX: cap attempts, log, return null.

F.11 Shared non-thread-safe System.Random
     PlayerFactoryEx.cs:21
     `private static readonly Random rand = new Random()` is the only RNG in
     Factories/ not using ThreadSafeRandom's ThreadLocal wrapper. Concurrent
     RandomizeHeritage calls can interleave into Random's internal state.
     FIX: switch to ThreadSafeRandom - remembering to use Count - 1, since it
     is inclusive.

F.12 RandomizeHeritage does not re-validate TemplateOption
     PlayerFactoryEx.cs:84-96
     It overwrites Heritage, Gender and appearance on a CharacterCreateInfo
     unpacked from the hardcoded Gear Knight blob but leaves TemplateOption
     alone. PlayerFactory.cs:135 then indexes
     heritageGroup.Templates[TemplateOption] against the NEW heritage's list,
     so any heritage with fewer templates than Gear Knight throws.
     FIX: clamp to Templates.Count - 1 after randomising.

SECTION E - SUGGESTED PRIORITY
================================================================================
  1. F.1  Chargen validation. It is the only remotely reachable finding here,
          it hangs the client with no error, and it permanently burns GUIDs
          from a finite range on every malformed packet.
  2. F.4  GetSpellLevels null guard - one content edit silently empties every
          corpse, which would be very hard to diagnose in the field.
  3. F.7  min > max amount - one bad DB row zeroes all loot for that profile.
  4. F.5  Uniform tier clamping - same class, unvalidated DB data reaching an
          array index.
  5. F.2, F.3 - the quality-modifier maths. These do not crash; they silently
          produce wrong loot (heavier items, guaranteed gear ratings), so they
          will be reported as "loot feels wrong" rather than as bugs.
  6. F.6, F.8-F.12 as follow-up.

NOTE: F.5 and F.7 share a root cause - treasure_death is world-DB content that
is trusted without validation. A single validation pass at load, rejecting or
clamping out-of-range tiers and inverted min/max amounts, would close both.

G.0  *** SEVERITY ESCALATION AFFECTING EVERY FINDING IN THIS DOCUMENT ***
     LootGenerationFactory.cs:40-104, Creature_Death.cs:653
     [VERIFIED DIRECTLY]

     CreateRandomLootObjects wraps all three category loops in:

         try { ... return loot; }
         finally { /* body is ENTIRELY COMMENTED OUT */ }

     There is NO CATCH. The try/finally is completely vestigial - it exists
     only to wrap a commented-out performance counter and provides zero
     protection.

     The propagation chain, traced end to end:
         LootGenerationFactory.CreateRandomLootObjects   (no catch)
           -> Creature_Death.GenerateTreasure:653        (unguarded)
             -> creature death handling
               -> the landblock tick
                 -> ActionQueue.RunActions, which per bugs-entity-server.txt
                    E.0d has NO EXCEPTION ISOLATION

     CONSEQUENCE: every throwing loot bug in this document does NOT merely
     produce an empty corpse, as previously documented. It escapes into the
     landblock tick and SKIPS EVERY REMAINING LANDBLOCK IN THAT GROUP for that
     frame.

     This re-rates F.0a (CantripChance NaN -> InvalidOperationException), F.4
     (GetSpellLevels NRE), F.5 (tier index out of range), F.7 (min>max
     ArgumentOutOfRangeException) and G.1/G.4/G.5 below. They are not
     "loot is empty" bugs; they are "part of the world stops ticking" bugs.

     FIX: a catch around the loop body in CreateRandomLootObjects that logs and
     returns the partial loot list. That is a strictly better failure mode than
     the current one, and it is a prerequisite for treating the rest of this
     document as merely-cosmetic. Fixing E.0d independently is still correct.


--- G: HIGH SEVERITY ---

G.1  [CORROBORATED BY BOTH PASSES] Null mutation filter dereferenced at every
     lootgen call site - and it is reachable by NORMAL PLAY
     LootGenerationFactory_Melee.cs:38-47, _Caster.cs:31-52, _Missile.cs:37-44,
     _Clothing.cs:135-137; engine at Entity/Mutations/MutationCache.cs:70-77

     MutationCache.GetMutation() returns NULL when the embedded script resource
     is missing - it logs and returns null. All five loot call sites then call
     mutationFilter.TryMutate(...) immediately with no null check.

     REACHABLE WITHOUT ANY BAD DATA: GetDamageScript (_Melee.cs:105)
     concatenates MeleeWeaponSkill.GetScriptName_Combined(), which returns null
     for any skill outside Heavy/Light/Finesse/TwoHanded
     (Factories/Enum/MeleeWeaponSkill.cs:48-60). Only 22 of the possible
     skill x weapon-type combinations ship as scripts - for example
     heavy_mace_jitte.txt does not exist, only light_finesse_mace_jitte.txt.

     So any world-DB weenie reachable through WeaponWcids whose WeaponSkill
     disagrees with the table that mapped its wcid produces a null filter and
     an NRE - which, per G.0, escapes into the landblock tick.

     Note RecipeManager.cs:1489-1495 DOES null-check the same call, and
     AssignArmorLevel (_Clothing.cs:122) DOES guard the null script name. The
     correct pattern exists twice in-tree.

     FIX: null-check the filter at each of the five sites (log and return), and
     make GetDamageScript fail closed when the skill name is null.

G.2  [VERIFIED DIRECTLY] Gems and dinnerware NEVER have their value mutated
     _Gem.cs:63, _Dinnerware.cs:59, gated by Entity/MutateFilters.cs:10-31

     Both call sites gate MutateValue behind
     `wo.HasMutateFilter(MutateFilter.Value)`. MutateFilters registers EXACTLY
     SIX filter ids - all armor (0x0E000012), shields (0x13) and weapons
     (0x14, 0x15, 0x16, 0x1D). The source comment even asks
     "only 6 mutate filter ids total in 16py?".

     Gems and dinnerware have no entry, so TryGetValue misses and the check
     returns false. They ALWAYS drop at base weenie value: tier, workmanship,
     material and gem class contribute NOTHING.

     ECONOMY IMPACT: a tier-8 diamond is worth exactly what a tier-1 one is.
     MutateValue_Gem (_Gem.cs:108) is consequently dead code.

     This is precisely why the equivalent check is COMMENTED OUT for
     weapons/armor/jewelry with `// fixme: data`
     (LootGenerationFactory.cs:101, _Melee.cs:91, _Jewelry.cs:70) - the same
     gap was already known there and worked around.

     FIX: comment out these two guards for consistency with the sibling
     factories, or seed MutateFilter data for non-equipment types.

G.3  [VERIFIED DIRECTLY] Dinnerware clobbers authored MaterialType
     _Dinnerware.cs:36

         wo.MaterialType = GetMaterialType(wo, profile.Tier);   // no > 0 guard

     Every sibling guards this: _Melee:59, _Missile:53, _Caster:56,
     _Jewelry:32, _Clothing:47 all use `if (materialType > 0)`. This is the
     same shape as the known F.9 cloak defect.

     GetDefaultMaterialType (LootGenerationFactory.cs:483-511) has NO BRANCH
     for WeenieType.Generic + ItemType.Misc, so dinnerware returns
     MaterialType.Unknown (0).

     FAILURE: a tier-3 porcelain goblet whose weenie lacks TsysMutationData
     loses its authored Porcelain, becomes Unknown - and then MutateColor
     (line 537) SKIPS ENTIRELY because it requires MaterialType > 0, so the
     item also loses its palette and icon roll, and salvages to nothing.

G.4  Effect.TryMutate NREs when an arithmetic operator returns null
     Entity/Mutations/Effect.cs:44-113, EffectArgumentOp.cs:344, 393, 442, 491

     The + - * / operators return NULL on unhandled type combinations.
     Effect.cs assigns that null to `result` and then
     Quality.StoreValue(wo, result) dereferences it. Validate (Effect.cs:118-130)
     deliberately does NOT check result.IsValid - the check is commented out at
     lines 120-124.

     FAILURE: a script line `FooBar += 5` where FooBar is not a known property
     enum gives GetStatType = Undef -> EffectArgumentType.Invalid ->
     ResolveValue leaves Type = Invalid -> `result + arg1` logs and returns
     null -> NRE, on the same escape path as G.0.

     FIX: bail out of TryMutate when any operator result is null, and
     re-enable the result.IsValid check.

G.5  Script parser crashes on truncated scripts AND caches partial parses
     Entity/Mutations/MutationCache.cs:112-113, 135, 150, 227, 230-231, 33-41

     `outcome.EffectLists.Last()` throws InvalidOperationException when a
     "Tier chances" block has no "- Chance" line - exactly what a TRUNCATED
     script produces. Line 227 NREs if an `X = 5` line precedes any
     "- Chance"; lines 135/150 NRE if "- Chance" precedes any "Tier chances".

     WORSE: every other parse error is only LOGGED, and the half-built
     MutationFilter is STILL CACHED. So a single bad line permanently produces
     silently wrong items - for example a mis-parsed Damage effect with
     StatIdx = 0 - with no runtime signal at all.

     MITIGATION: scripts are 95 .txt files embedded as ASSEMBLY RESOURCES
     (ReadScript uses GetManifestResourceStream), not loose operator-supplied
     files. So this is a shipped-content / patch-integrity concern rather than
     an untrusted-input one - lower risk than it first appears, but the parser
     is still unguarded.

     FIX: wrap BuildMutation in try/catch, guard .Last() with Count > 0, and
     track a hadErrors flag that makes the filter refuse to apply.

G.6  [VERIFIED DIRECTLY] Script number parsing is CULTURE-SENSITIVE on worker
     threads
     Entity/Mutations/MutationCache.cs:123, 159, 251, 266, 274 (and 305, 313)

     All script numeric parses use the culture-default float/decimal/double
     TryParse overloads. I confirmed the ONLY InvariantCulture in the entire
     Mutations directory is at line 558, for a hex parse.

     Program.cs:56 sets Thread.CurrentThread.CurrentCulture for the MAIN THREAD
     ONLY. .NET Core does not propagate that to landblock worker threads, and
     there is no DefaultThreadCurrentCulture anywhere in the tree.

     FAILURE: on a de-DE or fr-FR host, scripts compiled lazily on a worker
     thread parse `Damage += 1.5` as 15, and `Tier chances: 0.05` as 5 - so the
     mutation ALWAYS fires. Silent, host-dependent item corruption that would
     be extremely hard to diagnose from gameplay.

     FIX: CultureInfo.InvariantCulture on every TryParse, and set
     CultureInfo.DefaultThreadCurrentCulture at startup.

     (Same defect class as bugs-database.txt D.9, where culture-dependent float
     FORMATTING corrupts SQL export. Worth fixing as one sweep.)

G.7  SpellSelectionTable.Roll has no bounds check
     Tables/SpellSelectionTable.cs:437
         return spellSelectionGroup[spellCode - 1].Roll();
     No validation - unlike TreasureProfile_Item/MagicItem/Mundane.Roll, which
     all guard their profile index. Today spellCode comes from
     GetSpellSelectionCode_Dynamic (0-20, with 0 filtered at _Spells.cs:125),
     but the DOCUMENTED contract is `TsysMutationData >> 24` from the world DB.
     Any reintroduction of that path, or a new branch returning > 20, is an
     ArgumentOutOfRangeException per loot roll.
     FIX: range-check and return SpellId.Undef.

G.8  [VERIFIED DIRECTLY] AssignDivide is implemented as MULTIPLICATION
     Entity/Mutations/Effect.cs:107-110

         case MutationEffectType.AssignMultiply:
             result = arg1 * arg2;
             break;
         case MutationEffectType.AssignDivide:
             result = arg1 * arg2;      // <-- identical to the case above

     Any script of the form `X = A / B` produces A * B. No shipped script
     currently uses that form (all `/` uses are `/=`), so it is latent - but it
     is a silent stat-INFLATION landmine for any new or patched script.

G.9  Wrong DefaultMaterial row for thrown weapons
     LootGenerationFactory.cs:506
     WeenieType.Generic + ItemType.MissileWeapon reads DefaultMaterial[4],
     which LootTables.cs:16 labels DINNERWARE (Granite/Ceramic/Porcelain/
     Alabaster/Marble). Atlatl darts and throwing daggers therefore roll a
     ceramic material with MaterialTable value mods of 0.0-1.8. Index [1]
     (Missile: Oak/Teak/Mahogany/Pine/Ebony) is intended.

G.10 Non-magical items keep authored ManaRate inconsistently
     _Missile.cs:83, _Gem.cs:53, _Jewelry.cs:63 clear ManaRate = null in the
     non-magical branch. _Melee.cs:82-88, _Caster.cs:85-91 and _Clothing.cs:87-91
     do NOT. A non-magical tier-5 sword or breastplate therefore ships with a
     negative ManaRate and a null ItemMaxMana.

G.11 MutateCaster never calls MutateBurden
     _Caster.cs:73 has only the comment `// burden?`, while _Melee.cs:71 and
     _Missile.cs:72 both call MutateBurden(wo, profile, true). Casters are the
     only weapon class that never receives the quality-based burden reduction -
     a legendary-quality orb weighs exactly as much as a tier-1 one.

G.12 TryCreateRare luck can make rares GUARANTEED
     _Rare.cs:55, 59, with Corpse.cs:323-324
     Line 55 clamps `t1_chance = Max(t1_chance - luck, 1)`, and line 59 rolls
     `ThreadSafeRandom.Next(1, t1_chance) == 1` - which is ALWAYS TRUE when
     t1_chance == 1 (the RNG is inclusive on both bounds).
     Corpse.cs computes luck from a hardcoded t1_chance = 2500, while
     TryCreateRare derives its own from the rare_drop_rate_percent property.
     FAILURE: a server that LOWERS rare_drop_rate_percent (intending rarer
     rares) with realTimeRaresAlt enabled gets luck >= t1_chance, and therefore
     a tier-1 rare on EVERY eligible kill - the exact opposite of the intent.

G.13 Item count from the world DB is unbounded
     LootGenerationFactory.cs:51, 65, 79
