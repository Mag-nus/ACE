================================================================================
ACE.Adapter - BUG REPORT
================================================================================
Scope   : Source/ACE.Adapter  (78 files, ~6,400 lines)
          GDLE/ (GDLE emulator format), Lifestoned/ (Lifestoned content editor
          format), Enum/, top-level converters
Date    : 2026-07-25
Companion document: perf-adapter.txt

STATUS  : open findings only. Numbering is non-contiguous because resolved
          findings have been removed.

VERIFICATION
  TRACED BUT NOT RE-VERIFIED : all findings. Spot-check before fixing.


THEME: this code is almost entirely mechanical field-by-field mapping, which
makes it highly susceptible to copy-paste error. The dominant defect class is
SILENT DATA LOSS OR CORRUPTION - content passes through the converter and comes
out subtly wrong, with no error raised. Nothing here runs on a gameplay path,
so severity is scoped to "content is quietly damaged", not "server breaks".

The most productive technique was ROUND-TRIP ASYMMETRY: comparing the A->B
converter against B->A for the same type. Any property handled in one direction
but not the other is a data-loss bug. Most findings below came from that.
================================================================================


SECTION A - HIGH SEVERITY
================================================================================

A.1  Combined recipes all import with Id = 0
     GDLE/GDLELoader.cs:438-452

     TryLoadRecipeCombinedConverted calls TryConvert(value.recipe, ...) - which
     sets Id = input.recipe.RecipeId - instead of the RecipeCombined overload
     that does `recipe.Id = input.key`.

     ACE's own exporter deliberately zeroes that field
     (GDLEConverter.cs:440 `newRecipe.RecipeId = 0`), so a folder of
     ACE-exported combined recipes re-imports as N recipes ALL WITH Id 0, while
     the cookbooks correctly receive RecipeId = value.key and therefore point
     at recipes that do not exist.

     FIX: use GDLEConverter.TryConvert(value, out cookbooks, out recipe), or
     set result.Id = value.key.


A.5  Fractional spell fields typed as uint?, breaking the entire spell file
     GDLE/Models/Spell.cs:69, 72, 81, 108, 111, 117, 150

     CritFreq, CritMultiplier, ElementalModifier, SlayerDamageBonus,
     SpreadAngle, VerticalAngle, DefaultLaunchAngle and PowerVariance are
     double? or float? in ACE's Spell table - CritFreq is typically 0.03.

     The auditor verified that JsonSerializer.Deserialize THROWS JsonException
     on `"critFreq": 0.03` into a uint?. Because the loader catches and returns
     false, GDLELoader.TryLoadSpells / TryLoadSpellsConverted fails for the
     ENTIRE spell file with no error surfaced.

     FIX: type them double?.


SECTION B - MEDIUM SEVERITY
================================================================================

A.9  Unresolvable link endpoints are rewritten to 0 rather than dropped
     GDLE/GDLELoader.cs:133-144

     A links entry referencing a weenie not present in the same landblock file
     yields LandblockInstanceLink { ParentGuid = 0, ChildGuid = 0 }, which is
     STILL ADDED to the output list at lines 170-176 and inserted into the
     database as a dangling or self-referential link.

     FIX: skip the link when either lookup fails.


A.14 Missing JsonPropertyName attributes silently zero all body-part damage
     GDLE/Models/Zones.cs
     This is the ONLY model in the tree with no [JsonPropertyName] annotations.
     Its sibling ArmorValues is fully snake_case-annotated (base_armor,
     armor_vs_slash), so the bpsd sub-damage keys are almost certainly
     lower-case in the real format.
     System.Text.Json is CASE-SENSITIVE by default and LifestonedLoader passes
     no options (verified: `{"hlf":0.5}` deserialises to null), so all 12
     body-part damage zones import as 0 - LifestonedConverter.cs:130-144
     coerces null to 0. Creatures import with NO hit-location weighting.

A.15 A weenie with attributes but no vitals imports three zero-valued vitals
     GDLE/Models/AttributeSet.cs:26-34, Lifestoned/LifestonedConverter.cs:98-103
     AttributeSet initialises Health, Stamina and Mana to `new Vital()`.
     Import creates a MaxHealth/MaxStamina/MaxMana row for each non-null vital,
     so any file whose "attributes" object omits health, stamina or mana gets
     that vital as a row of zeros, because the omitted key deserialises to the
     default object, not null. Export has the same shape: a weenie with
     attributes and no vitals writes all three as zeros.
     NOT VERIFIED: whether a zero-valued vital row behaves differently from no
     row at runtime. Removing the initialisers changes how every existing file
     without vitals imports, so check that first.


SECTION C - GAPS: NO CONVERTER AT ALL
================================================================================
Not defects in existing code, but silent capability gaps worth recording.

G.1  Models/Encounter.cs and Models/Region.cs (EncounterMap, Encounters) are
     deserialised but have NO converter in either direction, and the GDLE model
     (key plus List<uint>) cannot express ACE's CellX/CellY encounter rows.
G.2  RecipeRequirementsString.Message is lost in BOTH directions, because
     Models/StringRequirement.cs has no Message field.
G.3  WeeniePropertiesCreateList.Palette is sbyte in ACE but uint? in
     CreateItem, so palette ids above 127 corrupt on import
     (LifestonedConverter.cs:161) and re-export as roughly 4.29 billion
     (line 647).
G.5  GDLE Spell.School (dispel school) is never written to Spell.DispelSchool -
     there is a TODO at GDLEConverter.cs:371 - so imported dispels lose their
     school filter.


SECTION D - INVESTIGATED, NOT A BUG
================================================================================
I.1  LifestonedConverter.cs:39 Enum.GetName(typeof(WeenieClassName), uint)
     against a ushort enum - verified on .NET 10 that GetName converts via
     UInt64 and returns the correct name. No exception.
I.2  LifestonedConverter.cs:43 input.Name NRE - LSDWeenie.Name is a computed
     property with a WeenieId.ToString() fallback, never null.
I.3  LifestonedConverter.cs:852 result.FloatStats.Add without initialising the
     list - LSDWeenie's stat lists all have field initialisers.
I.4  Emote Min/Max int?<->uint? casts - unchecked two's-complement round-trips
     exactly; only the intermediate JSON looks odd for negatives.
I.5  TreasureWielded (GDLEConverter.cs:1082) - all 19 columns mapped, and there
     is no ACE -> GDLE direction to be asymmetric with.
I.6  Event, Quest, RecipePrecursor and CookBook mappings are complete in both
     directions (Quest.MinDelta uint->int->uint round-trips unchecked).
I.7  Landblock re-guid logic runs twice (GDLELoader.cs:116 then
     GDLEConverter.cs:169) - the second pass is a no-op because the guids are
     already in range.
I.8  IsLinkChild is not set by GDLEConverter.TryConvert(Models.Landblock), but
     GDLELoader.TryConvertLandblocks:174-176 sets it for all callers that
     matter.


SECTION E - SUGGESTED PRIORITY
================================================================================
  1. A.5  uint? on fractional spell fields. It fails the ENTIRE spell file with
          no error surfaced, so a user importing spells gets silence and no
          spells. Highest impact-to-effort ratio here.
  2. A.14 Zones.cs missing annotations - every imported creature silently loses
          hit-location weighting, which would be extremely hard to diagnose
          from gameplay.
  3. A.1  Combined recipes importing with Id = 0 and orphaned cookbooks.
  4. A.15 after checking how zero-valued vitals behave.
  5. A.9 as robustness.
  6. Section C gaps as a separate piece of work.

RECOMMENDATION: the round-trip asymmetry technique found most of these, and it
is now mechanised - see roundtrip-adapter-tests.txt. Its remaining gaps are a
real content corpus, the JSON layer for the GDLE pairs (where A.5 and A.14
live) and the three one-way converters, including spells.
